# KubeClaw user stories

Stories generated by the system-improvement loop. Each story is followed by a status line:
- `status: drafted` — generated, no test yet
- `status: tested` — has a live test
- `status: passing` — test passes

## Story 1: Remove a channel via the admin shell

**As a** KubeClaw operator
**I want** to remove a channel (Deployment + K8s Secret + PVC) through the admin shell in a single command
**So that** I can cleanly decommission a channel without manually running multiple `kubectl delete` commands and risking orphaned resources

### Acceptance criteria

1. The admin shell exposes a `remove_channel` tool that accepts the channel instance name (e.g. `"telegram"`, `"http-staging"`).
2. Calling `remove_channel` deletes the channel Deployment, its associated K8s Secret (the one created by `setup_channel`), and its PersistentVolumeClaim — all in the same namespace as the orchestrator.
3. If any of those resources does not exist (already deleted or never created), the tool succeeds rather than erroring — it is idempotent.
4. The tool returns a human-readable summary listing exactly which resources were deleted and which were already absent.
5. After `remove_channel` completes, `kubectl get deployment,secret,pvc -n kubeclaw -l kubeclaw-channel=<instanceName>` returns no resources.

### Notes for the test author

- `setup_channel` is in `src/skills/orchestrator/channel-setup.ts`; it creates a Deployment named `kubeclaw-channel-<instanceName>`, a Secret named `kubeclaw-channel-<instanceName>-secret`, and (for applicable channel types) a PVC named `kubeclaw-channel-<instanceName>-data`. The label `kubeclaw-channel: <instanceName>` is applied to all three.
- The admin shell tool registry is in `src/admin-shell.ts` (the `TOOLS` array + the `handleTool` switch). A new `remove_channel` handler should mirror the structure of `remove_capability` (which calls `removeCapability` from `src/capabilities/index.ts`).
- The corresponding K8s delete calls should use the `CoreV1Api` (for Secrets and PVCs) and `AppsV1Api` (for Deployments) clients already instantiated at the top of `src/admin-shell.ts`.
- The existing e2e pattern to follow is `e2e/minikube-live-admin-shell.test.ts` — it helm-installs kubeclaw, port-forwards the admin Service (`kubeclaw-admin:9090`), and drives the admin shell via `POST /chat` + `GET /events` SSE. The live LLM is required for the natural-language dispatch path; alternatively, drive the tool directly via the JSON API if available.
- The test should: (a) call `setup_channel` (type `http`, minimal config) to create a channel, (b) verify the Deployment exists with `kubectl get`, (c) call `remove_channel` for that instance name, (d) verify all three resource kinds return 404 / no items. Use a unique instance name (e.g. `http-removeme`) to avoid collisions with the shared `kubeclaw-live` install.
- The tool must be idempotent: running `remove_channel` twice on the same instance name should not fail on the second call.
- Known constraint: the admin shell HTTP mode uses Basic Auth; credentials are in the cluster Secret `kubeclaw-secrets` key `admin-http-password` (see `minikube-live-admin-shell.test.ts` lines 57-63 for how to read it).

status: passing

## Story 2: Orchestrator Prometheus metrics endpoint is scrapeable after a tool-job runs

**As a** KubeClaw operator running Prometheus in my cluster
**I want** the orchestrator's `/metrics` endpoint to expose populated `kubeclaw_*` counters after real workload activity
**So that** I can scrape production metrics without needing to instrument the orchestrator separately and can alert on anomalies such as tool-job failures or queue saturation

### Acceptance criteria

1. After the kubeclaw helm chart is installed, `GET http://<orchestrator-metrics-service>:9091/metrics` returns HTTP 200 with `Content-Type: text/plain; version=0.0.4; charset=utf-8`.
2. The response body contains at least the metric families `kubeclaw_tool_job_spawned_total`, `kubeclaw_tool_job_duration_seconds`, `kubeclaw_redis_ipc_messages_total`, and `kubeclaw_group_queue_depth`.
3. After sending one message through the HTTP channel that causes a tool-job to be spawned (e.g. triggering a specialist or tool invocation that creates a Kubernetes Job), `kubeclaw_tool_job_spawned_total` increments by at least 1 in the subsequent scrape.
4. The metrics endpoint is exposed on the `kubeclaw-orchestrator-metrics` Service (or equivalent) on port 9091 and is reachable from within the cluster without authentication.
5. All four metric families remain present across a pod restart (metrics reset to zero is acceptable; the endpoint itself must still be up within 30 seconds of the pod becoming Ready).

### Notes for the test author

- The metrics server is created in `src/index.ts` via `createMetricsServer` from `src/metrics/registry.ts`. The port is controlled by `METRICS_PORT` (default `9091`). The Helm template in `helm/kubeclaw/templates/orchestrator.yaml` declares a `metrics` named port on the Deployment and a `metrics` Service port at `values.metrics.port` (default `9091`).
- Port-forward the orchestrator metrics Service for the test: `kubectl port-forward svc/kubeclaw-orchestrator -n kubeclaw-live 19091:9091` (pick a local port that doesn't conflict with the existing port-forwards in `e2e/minikube-live-setup.ts` which bind 14081 for the HTTP channel and 16381 for Redis).
- Metric names to assert in the text body: `kubeclaw_tool_job_spawned_total`, `kubeclaw_tool_job_duration_seconds_bucket`, `kubeclaw_redis_ipc_messages_total`, `kubeclaw_group_queue_depth`. All are registered in `src/metrics/orchestrator.ts`.
- To trigger `kubeclaw_tool_job_spawned_total` incrementing, post a message via the HTTP channel that the orchestrator dispatches to a Job; the easiest route is the `/alpine` specialist (or an equivalent Helm-time specialist) which spawns the kubeclaw-alpine Job image. Check `e2e/alpine-tool-execution.test.ts` for the POST pattern.
- The minikube-live global setup (`e2e/minikube-live-setup.ts`) helm-installs the cluster once per suite run; the metrics test can reuse that installation by following the `afterAll` / `beforeAll` pattern used in `e2e/minikube-live-rag.test.ts` (no separate helm install needed).
- Known constraint: `kubeclaw_group_queue_depth` is a Gauge that resets to 0 between messages; assert its presence (metric family name exists in the text) rather than a specific non-zero value.
- The pattern in `e2e/credential-injection.test.ts` line 325 shows the simplest approach: `execSync("curl -s http://localhost:19091/metrics", { encoding: "utf8" })` and `expect(metricsText).toContain("kubeclaw_tool_job_spawned_total")`. Adapt the same pattern for the orchestrator port.

status: passing (AC1-2, AC4-5; AC3 skipped — LLM dispatch dependency)
