# KubeClaw user stories

Stories generated by the system-improvement loop. Each story is followed by a status line:
- `status: drafted` — generated, no test yet
- `status: tested` — has a live test
- `status: passing` — test passes
- `status: shipped` — merged to main

## Story 1: Remove a channel via the admin shell

**As a** KubeClaw operator
**I want** to remove a channel (Deployment + K8s Secret + PVC) through the admin shell in a single command
**So that** I can cleanly decommission a channel without manually running multiple `kubectl delete` commands and risking orphaned resources

### Acceptance criteria

1. The admin shell exposes a `remove_channel` tool that accepts the channel instance name (e.g. `"telegram"`, `"http-staging"`).
2. Calling `remove_channel` deletes the channel Deployment, its associated K8s Secret (the one created by `setup_channel`), and its PersistentVolumeClaim — all in the same namespace as the orchestrator.
3. If any of those resources does not exist (already deleted or never created), the tool succeeds rather than erroring — it is idempotent.
4. The tool returns a human-readable summary listing exactly which resources were deleted and which were already absent.
5. After `remove_channel` completes, `kubectl get deployment,secret,pvc -n kubeclaw -l kubeclaw-channel=<instanceName>` returns no resources.

### Notes for the test author

- `setup_channel` is in `src/skills/orchestrator/channel-setup.ts`; it creates a Deployment named `kubeclaw-channel-<instanceName>`, a Secret named `kubeclaw-channel-<instanceName>-secret`, and (for applicable channel types) a PVC named `kubeclaw-channel-<instanceName>-data`. The label `kubeclaw-channel: <instanceName>` is applied to all three.
- The admin shell tool registry is in `src/admin-shell.ts` (the `TOOLS` array + the `handleTool` switch). A new `remove_channel` handler should mirror the structure of `remove_capability` (which calls `removeCapability` from `src/capabilities/index.ts`).
- The corresponding K8s delete calls should use the `CoreV1Api` (for Secrets and PVCs) and `AppsV1Api` (for Deployments) clients already instantiated at the top of `src/admin-shell.ts`.
- The existing e2e pattern to follow is `e2e/minikube-live-admin-shell.test.ts` — it helm-installs kubeclaw, port-forwards the admin Service (`kubeclaw-admin:9090`), and drives the admin shell via `POST /chat` + `GET /events` SSE. The live LLM is required for the natural-language dispatch path; alternatively, drive the tool directly via the JSON API if available.
- The test should: (a) call `setup_channel` (type `http`, minimal config) to create a channel, (b) verify the Deployment exists with `kubectl get`, (c) call `remove_channel` for that instance name, (d) verify all three resource kinds return 404 / no items. Use a unique instance name (e.g. `http-removeme`) to avoid collisions with the shared `kubeclaw-live` install.
- The tool must be idempotent: running `remove_channel` twice on the same instance name should not fail on the second call.
- Known constraint: the admin shell HTTP mode uses Basic Auth; credentials are in the cluster Secret `kubeclaw-secrets` key `admin-http-password` (see `minikube-live-admin-shell.test.ts` lines 57-63 for how to read it).

status: passing

## Story 2: Orchestrator Prometheus metrics endpoint is scrapeable after a tool-job runs

**As a** KubeClaw operator running Prometheus in my cluster
**I want** the orchestrator's `/metrics` endpoint to expose populated `kubeclaw_*` counters after real workload activity
**So that** I can scrape production metrics without needing to instrument the orchestrator separately and can alert on anomalies such as tool-job failures or queue saturation

### Acceptance criteria

1. After the kubeclaw helm chart is installed, `GET http://<orchestrator-metrics-service>:9091/metrics` returns HTTP 200 with `Content-Type: text/plain; version=0.0.4; charset=utf-8`.
2. The response body contains at least the metric families `kubeclaw_tool_job_spawned_total`, `kubeclaw_tool_job_duration_seconds`, `kubeclaw_redis_ipc_messages_total`, and `kubeclaw_group_queue_depth`.
3. After sending one message through the HTTP channel that causes a tool-job to be spawned (e.g. triggering a specialist or tool invocation that creates a Kubernetes Job), `kubeclaw_tool_job_spawned_total` increments by at least 1 in the subsequent scrape.
4. The metrics endpoint is exposed on the `kubeclaw-orchestrator-metrics` Service (or equivalent) on port 9091 and is reachable from within the cluster without authentication.
5. All four metric families remain present across a pod restart (metrics reset to zero is acceptable; the endpoint itself must still be up within 30 seconds of the pod becoming Ready).

### Notes for the test author

- The metrics server is created in `src/index.ts` via `createMetricsServer` from `src/metrics/registry.ts`. The port is controlled by `METRICS_PORT` (default `9091`). The Helm template in `helm/kubeclaw/templates/orchestrator.yaml` declares a `metrics` named port on the Deployment and a `metrics` Service port at `values.metrics.port` (default `9091`).
- Port-forward the orchestrator metrics Service for the test: `kubectl port-forward svc/kubeclaw-orchestrator -n kubeclaw-live 19091:9091` (pick a local port that doesn't conflict with the existing port-forwards in `e2e/minikube-live-setup.ts` which bind 14081 for the HTTP channel and 16381 for Redis).
- Metric names to assert in the text body: `kubeclaw_tool_job_spawned_total`, `kubeclaw_tool_job_duration_seconds_bucket`, `kubeclaw_redis_ipc_messages_total`, `kubeclaw_group_queue_depth`. All are registered in `src/metrics/orchestrator.ts`.
- To trigger `kubeclaw_tool_job_spawned_total` incrementing, post a message via the HTTP channel that the orchestrator dispatches to a Job; the easiest route is the `/alpine` specialist (or an equivalent Helm-time specialist) which spawns the kubeclaw-alpine Job image. Check `e2e/alpine-tool-execution.test.ts` for the POST pattern.
- The minikube-live global setup (`e2e/minikube-live-setup.ts`) helm-installs the cluster once per suite run; the metrics test can reuse that installation by following the `afterAll` / `beforeAll` pattern used in `e2e/minikube-live-rag.test.ts` (no separate helm install needed).
- Known constraint: `kubeclaw_group_queue_depth` is a Gauge that resets to 0 between messages; assert its presence (metric family name exists in the text) rather than a specific non-zero value.
- The pattern in `e2e/credential-injection.test.ts` line 325 shows the simplest approach: `execSync("curl -s http://localhost:19091/metrics", { encoding: "utf8" })` and `expect(metricsText).toContain("kubeclaw_tool_job_spawned_total")`. Adapt the same pattern for the orchestrator port.

status: passing (AC1-2, AC4-5; AC3 skipped — LLM dispatch dependency)
## Story 3: Global concurrency limit queues a third group's message until a slot opens

**As a** KubeClaw operator with multiple active users
**I want** the orchestrator to respect `MAX_CONCURRENT_JOBS` so that a third group's inbound message is held in the queue rather than dropped or processed out of turn when two groups are already running
**So that** busy periods are handled gracefully without losing messages and without overloading the node with unbounded parallel channel pods

### Acceptance criteria

1. With `orchestrator.maxConcurrentJobs=2` set at install time, when two groups each have a long-running tool job in flight, a POST to the HTTP channel from a third group receives HTTP 200 (message accepted) immediately — the channel does not reject or time out the request.
2. While those two jobs are in flight, the third group's message is not yet processed — the orchestrator has not produced any reply for the third group.
3. Once one of the two running jobs finishes and its slot is released, the third group's message is processed and a reply is produced within 30 seconds.
4. After all three groups have received replies, `kubectl get jobs -n <namespace>` shows at most 2 jobs with `status.active > 0` at any single point in time during the test (verified via log scraping or periodic polling).
5. No messages are lost: all three groups eventually receive a reply in the correct order (FIFO within a group).

### Notes for the test author

- `MAX_CONCURRENT_JOBS` is surfaced in the Helm chart as `orchestrator.maxConcurrentJobs` (default `10`; set to `2` for this test). The env var is injected in `helm/kubeclaw/templates/orchestrator.yaml` line 167-168. Use `--set orchestrator.maxConcurrentJobs=2` at helm install time.
- The `GroupQueue` implementation is in `src/group-queue.ts`. When `activeCount >= MAX_CONCURRENT_JOBS` the new group is added to `waitingGroups` and its `pendingMessages` flag is set; it is drained in `tryDrainWaiting()` once a slot frees. The test should verify this draining happens end-to-end.
- To create a long-running tool job, use a specialist or channel message that causes the orchestrator to dispatch a Kubernetes Job. The `/alpine` specialist (configured via `helm --set-json 'specialists=[...]'`) runs `sleep 10` via the kubeclaw-alpine image and is the simplest hold mechanism. Alternatively, configure a specialist whose system prompt instructs it to wait; a local stub LLM that responds slowly is another option.
- Port-forward the HTTP channel service to a local port (e.g. `14092` to avoid conflicts with the existing minikube-live suite on `14081`). The channel accepts `POST /message` with Basic Auth; see `e2e/minikube-live-admin-shell.test.ts` lines 57-63 for the Basic Auth pattern and `e2e/minikube-live.test.ts` for the POST + SSE reply pattern.
- Install kubeclaw in an isolated namespace (e.g. `kubeclaw-e2e-concurrency`) so the test does not collide with other suites. Follow the `beforeAll` / `afterAll` install+uninstall pattern from `e2e/credential-broker.test.ts`.
- Polling strategy for AC4: sample `kubectl get jobs -n kubeclaw-e2e-concurrency -o json` every second while the two jobs are running and assert `items.filter(j => j.status.active > 0).length <= 2`.
- Known constraint: job startup latency on kind can be 3-5 s; set SSE/reply timeouts to at least 60 s to avoid flaky failures on slow CI nodes.
- IMPORTANT: target the kind cluster `kubeclaw-e2e-istio` (not minikube). Install kubeclaw with default values (mode=sidecar). Use `KUBECLAW_SKIP_HELM_INSTALL=true` convention.

status: partial (3/5) — AC1 (POST 200), AC2 (queued state), AC4 (≤2 active jobs) pass; AC3, AC5 timing assertions flake on slow kind LLM (count-to-30 specialist exceeds 120s windows). Queue back-pressure logic verified structurally; LLM-end-to-end timing should be re-tested on a faster inference target.
## Story 4: Credential broker stamps Authorization header for allowed destinations and returns 403 for unknown ones (status: passing — 5/5)

**As a** KubeClaw operator relying on the credential-injection subsystem for secure LLM access
**I want** the credential broker to stamp a valid `Authorization: Bearer <key>` header when a registered pod presents a valid token for a known destination, and to return HTTP 403 when the same pod targets an unregistered destination
**So that** I can trust that the broker enforces the allow-list at runtime and that workloads cannot reach unlisted external endpoints by forging or omitting the credential header

### Acceptance criteria

1. A `kubectl run` curl pod presenting a valid ServiceAccount bearer token with `X-Forwarded-Authority: api.anthropic.com` receives HTTP 200 from `POST http://credential-broker.<ns>.svc:8080/authz` and the response includes an `Authorization` header whose value starts with `Bearer `.
2. The same pod presenting a valid bearer token with `X-Forwarded-Authority: unknown.example.com` (not in the broker config) receives HTTP 403 and the response body contains no `Authorization` header.
3. A request to `POST /authz` with no `Authorization` header at all (no bearer token) receives HTTP 401 regardless of the `X-Forwarded-Authority` value.
4. After the helm install, `GET http://credential-broker.<ns>.svc:9090/metrics` returns HTTP 200 and the body contains the metric family `credential_broker_authz_total` with labels reflecting the outcomes from AC1–AC3 (status=200, status=403, status=401).
5. The credential broker Deployment has `readyReplicas=1` within 60 seconds of `helm install` completing, and the pod's container is running as non-root (`runAsNonRoot: true` visible in the pod spec).

### Notes for the test author

- Install kubeclaw in an isolated namespace (e.g. `kubeclaw-e2e-authz`) with `orchestrator.replicas=0` (no orchestrator needed) and `secrets.existingSecret=kubeclaw-secrets` (pre-create the Secret with a dummy `anthropic-api-key`). Follow the `beforeAll` / `afterAll` pattern from `e2e/credential-broker.test.ts`.
- The broker's ConfigMap (`kubeclaw-credential-broker-config`) is rendered by `helm/kubeclaw/templates/credential-broker-config.yaml`. It includes built-in mappings for `api.anthropic.com` → `anthropic-api-key`. Pass `--set credentialInjection.mode=sidecar` so the broker is deployed.
- To call `/authz` from within the cluster, use `kubectl run --rm -i --restart=Never --image=curlimages/curl:8.10.1` — the curl pod runs in the same namespace and can resolve `credential-broker.<ns>.svc` via DNS. The existing `credential-broker.test.ts` line 100-111 shows this exact pattern.
- For AC1 (bearer token), the curl pod must present a real Kubernetes ServiceAccount bearer token. Use `--serviceaccount=kubeclaw-tool-job` (the SA created by the helm chart for tool jobs) and mount its token at the default path. Then retrieve the token with `kubectl exec ... -- cat /var/run/secrets/kubernetes.io/serviceaccount/token` and pass it as `-H "Authorization: Bearer <token>"`. Alternatively, use `kubectl create token kubeclaw-tool-job -n <ns> --audience kubeclaw-credential-broker` to mint a short-lived token before running the curl pod.
- For AC4 (metrics), port-forward `deployment/kubeclaw-credential-broker` on port 9090 and `curl -s http://localhost:<local>`. Use a distinct local port (e.g. `19092`) to avoid conflicts with Story 2's `19091`. The `credential_broker_authz_total` metric is registered in `src/credential-broker/metrics.ts`.
- For AC5, check `kubectl get pod -l app=kubeclaw-credential-broker -o jsonpath='{.items[0].spec.securityContext}'` — the rendered Deployment in `helm/kubeclaw/templates/credential-broker.yaml` sets `runAsNonRoot: true` and `runAsUser: 65534` at the pod level.
- Known constraint: the broker performs a TokenReview against the Kubernetes API for every `/authz` request; the `kubeclaw-credential-broker` ClusterRoleBinding (bound to `system:auth-delegator`) must exist before traffic is sent. This is installed by the helm chart automatically; wait for `kubectl rollout status deployment/kubeclaw-credential-broker` before running authz tests.
- IMPORTANT: target the kind cluster `kubeclaw-e2e-istio`. Install kubeclaw with default values (mode=sidecar) in an isolated namespace. Use `--set image.tag=e2e-test --set image.pullPolicy=IfNotPresent` (the kind cluster has `kubeclaw-orchestrator:e2e-test` pre-loaded). Use `KUBECLAW_SKIP_HELM_INSTALL=true` to bypass vitest globalSetup.

status: passing 5/5
## Story 5: Redis ACL user is created per tool-job and revoked on completion (status: passing 5/5)

**As a** KubeClaw operator running specialist tool jobs in my cluster
**I want** each tool-job pod to receive a unique, scoped Redis ACL user that is automatically revoked when the job finishes
**So that** a compromised or misbehaving tool-job cannot read other groups' streams, publish to foreign channels, or persist access to Redis after its lifetime ends

### Acceptance criteria

1. After a tool-job is spawned by the orchestrator, `redis-cli ACL LIST` (authenticated as admin) includes an entry for `sidecar-<jobId>` whose rules grant read access only to `kubeclaw:input:<jobId>` and publish access only to `kubeclaw:messages:<groupFolder>` — no other keyspace patterns are present.
2. A Redis client authenticating with the job's ACL credentials can execute `XREAD COUNT 1 STREAMS kubeclaw:input:<jobId> 0` and `PUBLISH kubeclaw:messages:<groupFolder> test` without error.
3. The same client is rejected (NOPERM error) when it attempts to read a different job's input stream (`kubeclaw:input:<otherJobId>`) or publish to a different group's channel.
4. After the orchestrator calls `revokeJobACL` for the job (either on job completion or on explicit revocation), `redis-cli ACL LIST` no longer contains `sidecar-<jobId>` and a subsequent authenticate attempt with the revoked credentials returns a `WRONGPASS` or `NOAUTH` error.
5. The ACL entry for the job is also recorded in the orchestrator's SQLite database (`job_acls` table) with `status='active'` during the job's lifetime and `status='revoked'` after revocation — confirming DB and Redis stay in sync.

### Notes for the test author

- The ACL manager is in `src/k8s/acl-manager.ts` (`RedisACLManager` class). Key methods: `createJobACL(jobId, groupFolder)`, `revokeJobACL(jobId)`, `getJobCredentials(jobId)`. The singleton is `getACLManager()`.
- DB helpers for ACL records are in `src/db.ts`: `storeJobACL`, `getJobACL`, `revokeJobACL` (marks status), `cleanupExpiredACLs`. The table is `job_acls`.
- Install kubeclaw in an isolated namespace (e.g. `kubeclaw-e2e-acl`) with `orchestrator.replicas=1`. Follow the `beforeAll`/`afterAll` helm install+uninstall pattern from `e2e/credential-broker.test.ts`. The Redis Service is `kubeclaw-redis:6379`; port-forward it to a local port (e.g. `16382`) — pick a port distinct from Story 2 (`19091`) and the existing suite ports.
- To read `redis-cli ACL LIST` from the test host, use `kubectl exec deployment/kubeclaw-orchestrator -n <ns> -- redis-cli -h kubeclaw-redis -p 6379 -a <adminPass> ACL LIST` (the admin password is in the `kubeclaw-secrets` Secret under key `redis-password`). Parse the output lines for the `sidecar-<jobId>` entry.
- For AC1–AC3, exercise the ACL manager directly: exec into the orchestrator pod and call a one-shot Node.js script that imports `RedisACLManager` and creates then verifies ACL entries. Alternatively, post an IPC message that triggers a real tool-job via the HTTP channel's specialist path and inspect the resulting ACL state with `redis-cli ACL LIST`. The second approach is more realistic but requires a registered specialist; the first is more targeted and LLM-free.
- For AC2–AC3 (permission checks), use `kubectl run --rm -i --restart=Never --image=redis:7-alpine` to run a transient Redis client pod in the same namespace. Pass job credentials via `--env`; then run `redis-cli -h kubeclaw-redis --user sidecar-<jobId> -a <password> XREAD ...`. Expect exit 0 for allowed ops and a `NOPERM` error string in stdout for denied ops.
- For AC5, exec into the orchestrator pod and run `sqlite3 /app/store/kubeclaw.db "SELECT status FROM job_acls WHERE job_id='<jobId>'"` before and after revocation to assert the status transitions from `active` to `revoked`.
- Known constraint: `ACL_ENCRYPTION_KEY` must be set (the helm chart injects it from `kubeclaw-secrets`). If the key is absent, the ACL manager falls back to a derived key (with a warning) — tests still pass but a warning is emitted in orchestrator logs.
- IMPORTANT: target the kind cluster `kubeclaw-e2e-istio`. Use `--set image.tag=e2e-test --set image.pullPolicy=IfNotPresent`. Service names in the chart are prefixed `kubeclaw-` (e.g. `kubeclaw-redis`, not `redis`). Use `KUBECLAW_SKIP_HELM_INSTALL=true` to bypass globalSetup.

## Story 6: Sender allowlist drop mode silently discards messages from blocked senders (status: passing 5/5)

**As a** KubeClaw operator who wants to limit which users can trigger the assistant
**I want** the channel pod to silently discard inbound messages from senders not on the allowlist when `mode` is `drop`
**So that** blocked senders get no response and generate no storage or LLM cost, without revealing that the block is in effect

### Acceptance criteria

1. When a `sender-allowlist.json` with `mode: "drop"` and an explicit sender list is written to the channel pod's config directory (`$HOME/.config/kubeclaw/sender-allowlist.json`), subsequent `POST /message` requests from a sender **not** in the list are silently discarded — no reply is produced and the message is not written to the SQLite database.
2. A `POST /message` from a sender **in** the allowlist is stored normally — `SELECT COUNT(*) FROM messages WHERE sender = '<allowed_sender>'` returns a non-zero count after the post.
3. Switching the file to `allow: "*"` (allow all) and posting from the previously blocked sender causes the message to be stored — confirming the config is re-read on each message rather than cached at startup.
4. When `mode: "trigger"` (not `drop`) and the sender is absent from the `allow` list, the message is still stored in the database — the trigger check only gates LLM dispatch, not storage.
5. The orchestrator debug log contains an entry with the text `sender-allowlist: dropping message` for every discarded message (verifiable via `kubectl logs`).

### Notes for the test author

- The allowlist config path in the pod is `$HOME/.config/kubeclaw/sender-allowlist.json`. In the kind cluster, `$HOME` inside the orchestrator/channel pod is `/root` (the container runs as root) or the configured user. Write it with `kubectl exec <pod> -- sh -c 'mkdir -p $HOME/.config/kubeclaw && cat > $HOME/.config/kubeclaw/sender-allowlist.json <<EOF\n{...}\nEOF'`.
- The drop logic is in `src/index.ts` around line 420 (`shouldDropMessage` + `isSenderAllowed`) and in `src/channel-runner.ts`. `loadSenderAllowlist()` reads the file fresh on every call — no restart needed after writing the file.
- To verify message storage, exec into the orchestrator pod and query SQLite: `kubectl exec deployment/kubeclaw-orchestrator -n kubeclaw-e2e-istio -- sqlite3 /app/store/kubeclaw.db "SELECT COUNT(*) FROM messages WHERE sender='blocked-user@example.com'"`. Expect `0` for the blocked sender and `>0` for the allowed sender.
- Use `KUBECLAW_SKIP_HELM_INSTALL=true` and target the pre-installed kubeclaw release in the `kubeclaw-e2e-istio` kind cluster. Port-forward the orchestrator's HTTP channel service to a local port (e.g. `14093`) using `kubectl port-forward svc/kubeclaw-orchestrator -n kubeclaw-e2e-istio 14093:14081`. The HTTP channel accepts `POST /message` with Basic Auth (credentials from Secret `kubeclaw-secrets`, key `http-channel-password`).
- AC3 (config hot-reload) is the key regression risk: do not add any in-memory caching of the allowlist in `loadSenderAllowlist()`. The unit test in `src/sender-allowlist.test.ts` already covers the load logic; the e2e test should verify the live file-write → message-drop cycle.
- For AC5, capture logs with `kubectl logs deployment/kubeclaw-orchestrator -n kubeclaw-e2e-istio --since=30s | grep "sender-allowlist: dropping"` immediately after posting a blocked message. Set `logDenied: true` in the allowlist JSON (it is the default).
- AC4 (trigger mode still stores) distinguishes `drop` from `trigger` mode: in `trigger` mode a denied sender's message reaches `storeMessage()` but does not proceed to the LLM queue. Assert the message row exists in SQLite but no SSE reply appears within a short timeout (e.g. 5 s).
- IMPORTANT: target the kind cluster `kubeclaw-e2e-istio`. Use `--set image.tag=e2e-test --set image.pullPolicy=IfNotPresent`. Service names in the chart are prefixed `kubeclaw-` (e.g. `kubeclaw-credential-broker`, `kubeclaw-orchestrator`, `kubeclaw-redis`). Use `KUBECLAW_SKIP_HELM_INSTALL=true` to bypass globalSetup. If installing via helm: pass `--create-namespace`.

status: passing 5/5

## Story 7: Idle per-group capability Deployments scale to zero after the configured idle timeout

**As a** KubeClaw operator running per-group capability pods (e.g. per-group MCP servers)
**I want** idle capability Deployments to be automatically scaled to zero replicas once `scaleDownAfterIdleSeconds` elapses without activity
**So that** capability pods do not consume compute and memory indefinitely when no group is using them

### Acceptance criteria

1. A per-group capability Deployment that has been idle (no `touchLastUsed` call) for at least `scaleDownAfterIdleSeconds` is scaled to zero replicas by the sweeper — verified by `kubectl get deployment <name> -o jsonpath='{.spec.replicas}'` returning `0`.
2. A per-group capability Deployment whose `lastUsedAt` was updated within the idle window is NOT scaled down — it retains `replicas=1`.
3. After scale-down, the SQLite row for that instance reflects `replicas=0` (query: `sqlite3 /app/store/kubeclaw.db "SELECT replicas FROM per_group_capability_instances WHERE deployment_name='<name>'"`).
4. A capability whose `scaleDownAfterIdleSeconds` is very large (e.g. `86400`) is not scaled down even when the same sweeper tick fires.
5. The orchestrator log contains an entry matching `per_group_capability_scale_down` with the correct `group` and `capability` fields for each Deployment that was scaled.

### Notes for the test author

- The sweeper implementation is in `src/per-group-capabilities/scale-down-sweeper.ts` (`sweepIdleInstances`). It reads live instances from `listInstancesAtReplicas(1)`, compares `lastUsedAt` against the spec's `scaleDownAfterIdleSeconds`, and calls `client.patchDeploymentReplicas(..., 0)` + `setReplicas(..., 0)` for any instance past the threshold. `nowSeconds` is injectable for time-control.
- DB helpers in `src/per-group-capabilities/db.ts`: `touchLastUsed(groupFolder, capabilityName)` updates `last_used_at`; `setReplicas(groupFolder, capabilityName, n)` updates the `replicas` column; `listInstancesAtReplicas(1)` returns all instances with `replicas=1`.
- This test is **LLM-free** and **Kubernetes-free** — use `FakePerGroupK8sClient` from `src/per-group-capabilities/k8s-client.ts` and `_initTestDatabase()` + `__resetDbForTest()` from `src/db.ts`. Call `sweepIdleInstances` directly; no helm install needed.
- Test setup pattern: (a) `_initTestDatabase()`, (b) `upsertInstance(...)` with `replicas=1`, (c) set `lastUsedAt` via `touchLastUsed` then manipulate time via the `nowSeconds` override to simulate elapsed idle, (d) call `sweepIdleInstances`, (e) assert `FakePerGroupK8sClient.deployments` and `listInstancesAtReplicas(0)`.
- To simulate log output for AC5, spy on `logger.info` (pino logger from `src/logger.ts`) and assert the call was made with `{ group, capability }` and message `'per_group_capability_scale_down'`.
- IMPORTANT: target kind cluster `kubeclaw-e2e-istio`. Use `--set image.tag=e2e-test --set image.pullPolicy=IfNotPresent --set credentialInjection.broker.image=kubeclaw-orchestrator:e2e-test`. Service prefix `kubeclaw-`. Use `--create-namespace`. Use `KUBECLAW_SKIP_HELM_INSTALL=true` for vitest run.

status: passing 4/4 — also surfaced + fixed chart RBAC gap (deployments/scale subresource was missing from kubeclaw-job-manager Role; sweep was silently no-op'ing in production)
## Story 8: Group credential secrets are created, listed, and deleted via the orchestrator IPC

**As a** KubeClaw operator configuring per-group LLM API keys or third-party credentials
**I want** the orchestrator to correctly create, list, and delete K8s Secrets for group credentials via the Redis IPC stream
**So that** channel pods can safely store per-group API keys in the cluster without any pod needing direct K8s API access

### Acceptance criteria

## Story 170: User asks for a sustained coding task — `execute_agent` spawns a nested pi-agent-core sub-agent

**As a** KubeClaw user with a programming task that needs more than a single shell command
**I want** to ask the assistant to do multi-step coding work in plain English ("@Andy refactor /data/util.py to use type hints and run the tests")
**So that** an `execute_agent` tool job spawns a nested `kubeclaw-agent` pod that runs its own agentic loop — picking up bash/read/write/edit and web tools, working against my group's PVC, and returning a final natural-language summary back into the channel's outer turn

### Background — what `execute_agent` actually is

`execute_agent` is the only tool in `src/runtime/direct-llm-runner.ts` that escalates from a single-shot tool pod (bash/web_fetch/etc.) to a **full nested agent loop**. It is not Claude Code, and KubeClaw has no Claude Code dependency at runtime — Claude Code is purely an operator-side tool (`/customize`, `/debug`, admin-shell guidance).

The flow:

1. Channel pod's `DirectLLMRunner` receives the tool call, generates a tool-job id (`agent-<ts>-<rand>`), and either runs the job directly (orchestrator mode) or publishes a spawn request to the `kubeclaw:toolcalls:spawn-agent` Redis stream (channel mode). The channel pod then blocks on `kubeclaw:toolresults:<jobId>` for the final string. See `executeToolJob()` in `src/runtime/direct-llm-runner.ts:618`.
2. The orchestrator's `jobRunner.runToolJob()` (in `src/k8s/job-runner.ts`) creates a Kubernetes Job using the image returned by `getContainerImage(group.llmProvider)` (`src/config.ts:121`). Default mapping: `claude → kubeclaw-agent:claude`, `openrouter → kubeclaw-agent:openrouter`, others → `kubeclaw-agent:latest`. The image is built from `container/agent-runner/`.
3. Inside the pod, `container/agent-runner/src/index.ts` uses `@mariozechner/pi-agent-core` to run the agent loop. Tool dispatch fans out over Redis streams:
   - Execution tools (`bash`, `read`, `write`, `edit`, `glob`, `grep`) → `kubeclaw:toolcalls:<jobId>:execution` → a sibling **execution** tool-pod running `tool-server.ts` → `kubeclaw:toolresults:<jobId>:execution`.
   - Browser tools (`web_fetch`, `web_search`, `agent_browser`) → `kubeclaw:toolcalls:<jobId>:browser` → a sibling **browser** tool-pod → `kubeclaw:toolresults:<jobId>:browser`.
   - IPC tools (`send_message`, `schedule_task`, …) → Redis pub/sub directly, no extra pod.
4. Follow-up messages from the channel to the in-flight agent travel on `kubeclaw:input:<jobId>`.
5. When the loop finishes, the agent pod publishes the final result (one record on `kubeclaw:toolresults:<jobId>` with `result` + `status` fields) and exits. The channel pod's blocked `xread` unblocks and feeds the result back to the outer LLM as a normal tool result string.

This means a single `execute_agent` call typically materializes **three pods**: the agent-runner itself, an execution tool-pod sidekick, and (if any web tool is used) a browser tool-pod sidekick. The credential broker sidecar is injected into the agent-runner pod because that's where outbound LLM calls originate; the execution/browser pods don't need it.

No `bash` or `mcp__filesystem__*` calls in the same turn — those would short-circuit the agent path.
2. **Pod fan-out** — within 30 s of the tool call, three pods exist:

   - One labelled `kubeclaw.io/category=execution`, `kubeclaw.io/tool-job-id=<jobId>` (the execution tool-server sidekick, started lazily on first execution-tool call).
   - The agent-runner pod has the credential-broker sidecar container `credential-broker` (when `credentialInjection.mode=sidecar`).

## Story 174: Admin bootstraps a new channel via a skill — slim generic pod installs its own packages, configures, then drops superuser

**As a** KubeClaw operator setting up a new channel without remembering the per-type credential prompts, env-var names, package dependencies, and Secret/PVC/Deployment plumbing
**I want** to invoke a single admin-shell IPC tool that spawns a *slim* generic agent pod, hands it a "set up channel X" skill plus temporary superuser, and lets it install the channel's npm dependencies onto a PVC, gather credentials from me interactively, then hand off to a steady-state channel pod that mounts the same PVC read-only
**So that** my cluster doesn't carry one fat image with every supported channel's libraries baked in — each channel install is materialised on-demand into its own per-channel runtime PVC — and the resulting steady-state pod is provably non-privileged, with the npm registry firewalled off and no residual superuser capability

### Background — the lifecycle this story introduces

Today, every channel TYPE (`telegram`, `irc`, `oauth-webchat`, `http`) is compiled into the orchestrator image. Its npm dependencies (`irc-upd`, `openid-client`, etc.) are dependencies of the top-level `package.json` and ship in every kubeclaw deployment regardless of which channels the operator actually uses. `setup_channel` (`src/skills/orchestrator/channel-setup.ts`) creates a Deployment from that same image, sets `KUBECLAW_MODE=channel` and `KUBECLAW_CHANNEL_TYPE=<type>`, runs `node dist/channel-runner.js`, and the runtime picks the right channel TYPE off the registry.

This story replaces *both* the gathering phase *and* the image's coupling to channel-specific libraries. The pieces:

1. **A new slim base image** — `kubeclaw-channel-base:*`. Contains: Node runtime, npm, the kubeclaw IPC / Redis / credential-broker plumbing, the agent-runner core (`@mariozechner/pi-agent-core`), and a small `channel-loader.js` entrypoint that knows how to load a channel TYPE from a PVC path. It contains **no channel-specific dependencies** — no `irc-upd`, no Telegram SDK, no `openid-client`. The image is intentionally cache-friendly and a fraction of the current orchestrator image size.
2. **A per-channel runtime PVC** — `kubeclaw-channel-<instance>-runtime`, mounted into both the bootstrap pod (read-write) and the steady-state pod (read-only). It holds the channel's `node_modules/`, the channel's TypeScript-compiled-to-JavaScript entry file (e.g. `channel-entry.js`), and a pinned `package-lock.json`. This PVC is the **carrier** between bootstrap and steady-state — bootstrap writes it; steady-state reads it.
3. **A new admin-shell IPC tool** — `bootstrap_channel_from_skill(skill_name, channel_type, instance_name, channel_credentials_hint?)`. Registered next to `setup_channel` in `src/admin-shell.ts`.
4. **Bootstrap mode in `channel-loader.js`** — recognised via `KUBECLAW_BOOTSTRAP_SKILL`. When set, the entrypoint *does not* try to load a channel; instead it runs the agent-runner loop with `KUBECLAW_SUPERUSER=true`, loads the named skill markdown from a mounted ConfigMap, and registers a `commit_channel_config` IPC tool that requests hand-off from the orchestrator. When unset, the entrypoint loads `/runtime/channel-entry.js` from the per-channel PVC and runs it under the regular channel-runner path — no agent loop, no `local_*` tools, no superuser.
5. **Per-channel-type package manifests** — each supported channel type ships with a tiny manifest (`channel-manifests/<type>.json` in the orchestrator image) listing its npm dependencies with pinned versions and an integrity-hashed `package-lock.json`. The bootstrap pod follows the skill to `npm ci --prefix /runtime` against this manifest. The manifest is signed/checksum-verified before install. Channel source code lives in scoped npm packages — e.g. `@kubeclaw/channel-telegram` — published to the operator's registry of choice. The skill names the package; it does not embed the source.
6. **Hand-off via `commit_channel_config`** — orchestrator validates the payload, creates the steady-state Deployment using `kubeclaw-channel-base:*` with the runtime PVC mounted read-only at `/runtime`, command `node /runtime/channel-entry.js`. The bootstrap pod terminates cleanly. The steady-state Deployment has *no* network egress to npm (NetworkPolicy denies); only the bootstrap Job's egress allowlist permits the registry.

The architectural shape — slim base image + per-channel runtime PVC + bootstrap-time `npm ci` + steady-state read-only mount — means the operator's cluster grows only the channels they actually install, the install path is reproducible from a lockfile, and the running channel pod can never re-install or modify its own runtime.

### Acceptance criteria

1. **Slim base image inventory.** The `kubeclaw-channel-base:*` image's `node_modules/` contains the runtime + IPC + agent-runner core dependencies, but **none** of the channel-specific libraries. Verifiable via `docker run --rm kubeclaw-channel-base:<tag> npm ls --depth=0 --json` returning a tree that does not include `irc-upd`, `openid-client`, `@telegraf/*`, `discord.js`, or `@slack/*`. The image size is at least 30% smaller than today's orchestrator image (concrete number: under 250 MiB uncompressed; measured via `docker image inspect`).

2. **New IPC tool + bootstrap Job spec.** `src/admin-shell.ts` exposes `bootstrap_channel_from_skill(skill_name, channel_type, instance_name, channel_credentials_hint?)`. Calling it:
   - Returns a `bootstrapJobId` synchronously.
   - Creates a per-channel runtime PVC named `kubeclaw-channel-<instance>-runtime` (RWO, 1 GiB default, sized from skill frontmatter).
   - Creates a Kubernetes **Job** `kubeclaw-bootstrap-<instance>` using image `kubeclaw-channel-base:<tag>` with envs `KUBECLAW_SUPERUSER=true`, `KUBECLAW_BOOTSTRAP_SKILL=<skill_name>`, `KUBECLAW_BOOTSTRAP_CHANNEL_TYPE=<channel_type>`, `KUBECLAW_BOOTSTRAP_INSTANCE=<instance_name>`; the runtime PVC mounted read-write at `/runtime`; a ConfigMap volume at `/workspace/skills/` holding the skill markdown; the channel-manifests ConfigMap at `/workspace/manifests/`; the credential-broker sidecar.

3. **Package install with supply-chain controls.** The bootstrap skill instructs the agent to run `local_bash` invocations equivalent to `cp /workspace/manifests/<channel_type>/{package.json,package-lock.json} /runtime/ && cd /runtime && npm ci --omit=dev --ignore-scripts`. The install must:
   - Use `npm ci` (lockfile-driven) — not `npm install` — so the resolved versions are deterministic.
   - Run with `--ignore-scripts` to suppress arbitrary `postinstall` hooks; the orchestrator rejects manifests whose packages require lifecycle scripts (allowlist in `helm/kubeclaw/values.yaml` if any package needs them).
   - Succeed only with NetworkPolicy egress permitting `registry.npmjs.org:443` (or the operator-configured mirror in `values.yaml: bootstrap.npmRegistry`); the same egress is **denied** for steady-state channel pods.
   - Result in `/runtime/node_modules/<channel-package>` being present with a verified `package-lock.json` integrity hash matching the manifest.
   The skill is not free to install arbitrary packages — it can only request what's in `/workspace/manifests/<channel_type>/package.json`, which is signed via a manifest checksum the orchestrator embeds at chart install time. If the skill tries `npm install <other-package>`, the bootstrap pod's NetworkPolicy still permits the registry but the orchestrator rejects the eventual `commit_channel_config` call because the runtime PVC diverges from the manifest hash.

4. **Interactive dialogue + hand-off.** The bootstrap pod's first agent-loop turn surfaces in the admin shell SSE via the Redis bridge (topic `kubeclaw:bootstrap:<bootstrapJobId>`). The admin answers questions; the agent writes Secret data and a config object under `/runtime/config/`, validates them with `local_bash` (e.g. `curl https://api.telegram.org/bot<token>/getMe` through the credential broker), then calls `commit_channel_config(channel_type, instance_name, secret_data, runtime_pvc_lock_hash)`. The orchestrator:
   - Verifies `runtime_pvc_lock_hash` matches the expected hash for `channel_type` (rejects if the bootstrap deviated from the pinned manifest).
   - Creates the K8s Secret with `secret_data`.
   - Creates the steady-state **Deployment** `kubeclaw-channel-<instance>` using image `kubeclaw-channel-base:<tag>`, command `["node", "/runtime/channel-entry.js"]`, with the runtime PVC mounted **read-only** at `/runtime`, no `KUBECLAW_SUPERUSER`, no `KUBECLAW_BOOTSTRAP_SKILL`.
   - Returns success to the bootstrap pod; the bootstrap Job exits 0 and is GC'd after `bootstrapJobTtlSeconds` (default 3600).
   - Sends a final SSE message to the admin: "Channel <type>/<instance> ready."

5. **No residual superuser, no residual install capability.** After hand-off:
   - The steady-state pod's spec has no `KUBECLAW_SUPERUSER` env (verifiable via `kubectl get pod -l kubeclaw-channel=<instance> -o jsonpath`).
   - The runtime PVC is mounted with `readOnly: true` on the steady-state pod; an exec'd `touch /runtime/x` returns EROFS.
   - The steady-state pod's NetworkPolicy denies egress to the npm registry (`registry.npmjs.org` and the configured mirror); verifiable via `kubectl exec ... -- curl --max-time 5 https://registry.npmjs.org` failing with timeout / blocked.
   - The image pulled is `kubeclaw-channel-base:<tag>`, not any image variant that contains channel libraries baked in.
   - Inbound channel traffic round-trips end-to-end: a test message reaches the channel pod, is processed via the dynamically-loaded channel TYPE, and the orchestrator records a reply (regression test against today's `setup_channel`-produced channels).

## Story 175: Bootstrap timeout atomically cleans up the partial channel install

**As a** KubeClaw operator who abandoned a bootstrap dialogue partway through (closed the terminal, lost their session, or simply walked away),
**I want** the cluster to silently roll back to a clean state when the bootstrap Job's deadline fires — deleting the Job, the runtime PVC, and any partially-created Secret
**So that** there is no orphaned PVC consuming storage, no dangling Secret with partial credentials, no stale "already in progress" lock, and I can immediately retry `bootstrap_channel_from_skill` with the same instance name without manual cluster surgery.

### Background — what can go wrong before this story

Story 174 creates three durable cluster objects during a bootstrap: the runtime PVC (`kubeclaw-channel-<instance>-runtime`), the bootstrap K8s Job (`kubeclaw-bootstrap-<instance>`), and, only on successful `commit_channel_config`, a K8s Secret. If the admin closes their shell without completing the dialogue, Kubernetes fires the Job's `activeDeadlineSeconds` deadline, which terminates the pod. Without this story, the orchestrator process never learns the Job died, the runtime PVC sits orphaned consuming storage (default 1 GiB), the in-memory "already in progress" map retains the instance name indefinitely (cleared only on orchestrator restart), and the admin receives no notification. This story closes that gap.

### Acceptance criteria

1. **`DeadlineExceeded` watcher in `bootstrap-runner.ts` triggers cleanup.** `src/k8s/bootstrap-runner.ts`'s `waitForBootstrapJobCompletion` path already calls `waitForJobCompletion` from `src/k8s/job-runner.ts` and catches `DeadlineExceededError`. When that error is caught, it must call a new `cleanupBootstrapResources(bootstrapJobId, instanceName)` function (also in `bootstrap-runner.ts`) before returning. `cleanupBootstrapResources` must execute the following steps in order, each wrapped in a `try/catch` that logs a warning on failure but continues to the next step: (a) delete the K8s Job `kubeclaw-bootstrap-<instanceName>` via `JobRunner.stopJob` (NotFound is silently swallowed — idempotent); (b) delete the PVC `kubeclaw-channel-<instanceName>-runtime` via `CoreV1Api.deleteNamespacedPersistentVolumeClaim` with `gracePeriodSeconds=0` (NotFound silently swallowed); (c) delete the K8s Secret `kubeclaw-channel-<instanceName>-credentials` if it exists (defensive — Story 174's `commit_channel_config` creates the Secret, which would not have fired in a timeout path, but the cleanup must check; NotFound silently swallowed). Only after all three deletion attempts does the function proceed to steps (d) and (e).

2. **Admin receives a final SSE timeout notice.** After resource deletion attempts complete, `cleanupBootstrapResources` publishes a message to Redis topic `kubeclaw:bootstrap:<bootstrapJobId>` (the same topic the bootstrap dialogue uses per Story 174 AC4) with payload `{ type: 'timeout', text: 'Bootstrap <bootstrapJobId> timed out; nothing was installed.' }`. The publish is best-effort — if it fails, the failure is logged at warn level and does not abort cleanup. The admin shell's SSE stream, which is subscribed to that topic via the bridge in `src/k8s/ipc-redis.ts`, delivers the message as a final SSE event to any connected admin client. If no admin client is connected, the message is dropped (pub/sub, not a stream — this is acceptable; the admin will observe the absence of a steady-state Deployment as confirmation).

3. **Instance name freed; retry is clean.** `bootstrap-runner.ts` maintains an in-memory `activeBootstraps: Map<string, string>` (`instanceName → bootstrapJobId`) that `bootstrap_channel_from_skill` checks to enforce the "already in progress" guard (Story 174 AC2). `cleanupBootstrapResources` must delete the entry from this map as its final step (after the Redis publish), regardless of whether the preceding deletion steps succeeded or failed. A subsequent call to `bootstrap_channel_from_skill` with the same `instanceName` must succeed — creating a fresh PVC, Job, and `bootstrapJobId` — without any "already in progress" error. Unit tests cover this by calling `cleanupBootstrapResources` directly against a fake `activeBootstraps` map and asserting the entry is absent afterwards.

4. **Orchestrator restart mid-cleanup is idempotent (orphan-bootstrap pattern).** On orchestrator startup, a new `reconcileOrphanedBootstrapsOnStartup` function in `bootstrap-runner.ts` queries the cluster for Jobs with label `kubeclaw.io/role=bootstrap` that are in terminal state (`status.conditions[].type=Failed`, `reason=DeadlineExceeded`) and whose corresponding instance names are not present in `activeBootstraps` (because the map was empty at startup). For each such orphan, it calls `cleanupBootstrapResources` with a synthesised `bootstrapJobId` derived from the Job's `kubeclaw.io/bootstrap-job-id` label (stamped on the Job at creation by `bootstrap_channel_from_skill`). The function is bounded by the same `timeoutMs` pattern used in `reconcileOrphanedJobsOnStartup` in `src/k8s/orphan-jobs.ts` (default 30 s, injected for tests). This ensures a cluster that processed a deadline while the orchestrator was down never leaves behind a stale PVC or Secret after the next restart.

5. **`BOOTSTRAP_SKILL_TIMEOUT_SECONDS` is honoured end-to-end.** The existing `BOOTSTRAP_SKILL_TIMEOUT_SECONDS` environment variable (introduced in Story 174 AC2 as the configurable override for `activeDeadlineSeconds=900`) must also govern the orchestrator-side polling timeout passed to `waitForJobCompletion`. Today's `waitForJobCompletion` in `job-runner.ts` takes an explicit `timeoutMs` parameter; `waitForBootstrapJobCompletion` in `bootstrap-runner.ts` must pass `BOOTSTRAP_SKILL_TIMEOUT_SECONDS * 1000 + 60_000` (a 60-second grace period above the Job deadline to account for K8s condition propagation latency). If `BOOTSTRAP_SKILL_TIMEOUT_SECONDS` is not set, the default is 900 s. Verifiable: setting `BOOTSTRAP_SKILL_TIMEOUT_SECONDS=60` in the e2e test reduces the effective timeout to 120 s, allowing the test to observe the full timeout→cleanup→retry cycle within a two-minute wall-clock budget.

3. **`register_bootstrap_skill` rejects malformed frontmatter with a precise error naming the offending field, and the ConfigMap is not modified.** Each of the following inputs must be rejected before any SQLite write or ConfigMap patch is issued, with the indicated error text: (a) `name` in the frontmatter does not match the `name` argument → `"frontmatter name mismatch: expected <arg>, got <fm.name>"`; (b) `description` absent or blank → `"frontmatter missing required field: description"`; (c) `bootstrap.channelType` absent or blank → `"frontmatter missing required field: bootstrap.channelType"`; (d) `bootstrap.manifestVersion` does not correspond to any registered manifest for the declared `channelType` → `"bootstrap.manifestVersion does not match any registered manifest for channelType=<type>"`; (e) `bootstrap.expectedQuestions` absent, not an array, or empty → `"frontmatter missing required field: bootstrap.expectedQuestions (must be a non-empty array)"`; (f) a skill whose frontmatter parses cleanly but whose `bootstrap.channelType` contains a typo (e.g. `"telegramm"`) must be rejected at `register_bootstrap_skill` call time with error (d) and must never appear in the `kubeclaw-bootstrap-skills` ConfigMap. This last assertion — that the typo-carrying skill is absent from the live ConfigMap — is the load-bearing check for the "fail at upload, not at use" guarantee.

4. **`register_bootstrap_skill` is idempotent on (name, identical content) — a second call with the same markdown does not bump the ConfigMap `resourceVersion`.** When the `sha256(markdown)` of the incoming payload matches the hash already stored in the `bootstrap_skill_overrides` SQLite table for the given `name`, the tool short-circuits: it returns `{name, content_hash, source: "admin-registered"}` without issuing a Kubernetes ConfigMap patch. The ConfigMap's `metadata.resourceVersion` is unchanged, verifiable by reading `kubectl get configmap kubeclaw-bootstrap-skills -o jsonpath='{.metadata.resourceVersion}'` before and after the second tool call and asserting the two values are identical. A second call with the same `name` but different markdown content must proceed through full validation and, if valid, overwrite the SQLite entry and trigger a ConfigMap reconcile — the returned `content_hash` changes and the ConfigMap `resourceVersion` is bumped.

5. **`remove_bootstrap_skill(name)` removes admin-registered skills but refuses Helm baseline skills with a structured error, and is idempotent on already-removed admin entries.** When called for an admin-registered skill, the tool deletes the `bootstrap_skill_overrides` SQLite row, triggers reconcile, and returns `{name, status: "removed"}`. When called for a Helm baseline skill (identified by its absence from `bootstrap_skill_overrides` combined with its presence in the baseline loader output), the tool returns without modifying any state: `{code: "PROTECTED_BASELINE", source: "helm-baseline", name}`. When called a second time for an already-removed admin skill (or any name that does not exist in either the overrides table or the baseline), the tool returns `{name, status: "already absent"}` — no error, no exception. All three outcomes are verified in a single test scenario: register a skill, remove it once (status=removed), remove it again (status=already absent), then attempt to remove a Helm baseline skill name and assert the `PROTECTED_BASELINE` response and confirm the ConfigMap still contains the baseline skill.

## Story 180: `bootstrap_status` surfaces in-progress and recently-completed bootstraps

**As a** KubeClaw operator who has triggered one or more channel bootstraps
**I want** an `admin-shell` IPC tool that returns a structured snapshot of every active bootstrap and every recently-completed one — in a single call, without touching `kubectl` or decoding cluster primitives manually
**So that** I can check bootstrap progress after closing and reopening my terminal, compare outcomes across multiple concurrent installs, and confirm that timed-out or rejected bootstraps cleaned up correctly, all through the same admin-shell interface I use for every other cluster operation

### Background

Story 174's `bootstrap_channel_from_skill` hands back a `bootstrapJobId` and bridges the bootstrap pod's dialogue to the admin shell SSE stream. That stream is ephemeral: if the admin closes their terminal, progress is invisible until the steady-state Deployment appears (or doesn't). Stories 175 and 176 add terminal-state paths (timeout, manifest-divergence) that also emit a single SSE event — equally losable. Today the only durable signal is the raw cluster state (`kubectl get jobs`, `kubectl get pvc`). This story adds a first-class polling tool, `bootstrap_status`, that joins the in-memory `activeBootstraps` map, the Kubernetes API, and a new SQLite `bootstrap_history` table into one structured response, and adds a lightweight `report_step` IPC tool the bootstrap skill can call to annotate its own progress mid-run.

### Acceptance criteria

1. **In-progress bootstraps appear in `active[]` with state derived from the dialogue topic and pod phase.** `bootstrap_status()` queries the in-memory `activeBootstraps: Map<string, string>` (Story 175 AC3) and, for each entry, reads the most-recent message published on `kubeclaw:bootstrap:<bootstrapJobId>` from `src/k8s/ipc-redis.ts` plus the current K8s pod phase via `BatchV1Api` / `CoreV1Api`. It returns one entry per active bootstrap with the shape `{bootstrapJobId, channelType, instanceName, skillName, startedAt, elapsedSeconds, state, currentStep, podPhase, logsTail?}`. The `state` field is a string enum: `awaiting-dialogue` (the bootstrap pod sent a question and is waiting for an admin reply), `installing-packages` (the skill has issued the `npm ci` step and the pod is in Running phase), `validating-credentials` (post-install, pre-commit validation round-trip in progress), `committing` (the skill has called `commit_channel_config` and the orchestrator has not yet responded), `done` (commit succeeded, bootstrap pod is exiting), `error` (pod phase is Failed or the bootstrap pod published an error event). The `currentStep` field is a free-text label last published by the skill via the `report_step` IPC tool (see below); if no `report_step` has been called, `currentStep` defaults to a human-readable label derived from `state` (e.g. `state: "installing-packages"` → `currentStep: "Installing packages"`). The full state machine — including each of the six states — must be exercised by unit tests in `src/k8s/bootstrap-runner.test.ts` using a stubbed Redis subscriber and stubbed K8s client.

2. **Completed bootstraps appear in `recent[]` with the correct outcome and persist across orchestrator restart.** `recent[]` is populated from a new SQLite table `bootstrap_history(bootstrap_job_id TEXT PRIMARY KEY, channel_type TEXT NOT NULL, instance_name TEXT NOT NULL, skill_name TEXT NOT NULL, manifest_hash TEXT, started_at TEXT NOT NULL, completed_at TEXT NOT NULL, outcome TEXT NOT NULL, error_code TEXT, error_message TEXT)` added via a migration in `src/db.ts`. The `outcome` column is a string enum: `succeeded` (populated by `commit_channel_config` success path), `timed-out` (populated by Story 175's `cleanupBootstrapResources`), `manifest-divergence` (populated by Story 176's rejection cascade), `rejected` (populated by any other orchestrator-side hard rejection), `error` (populated by an unhandled terminal failure). A new `recordBootstrapTerminal(bootstrapJobId, outcome, errorCode?, errorMessage?)` function in `src/k8s/bootstrap-runner.ts` performs the SQLite `INSERT OR REPLACE` and is called from each terminal path (success, timeout, divergence, rejection, error). The orchestrator restart persistence guarantee is validated in a dedicated e2e test case: insert a row directly into SQLite, restart the orchestrator Deployment via `kubectl rollout restart`, call `bootstrap_status`, and assert the entry appears in `recent[]` with correct fields.

3. **`limit` and `channel_type_filter` parameters compose cleanly for both `active[]` and `recent[]`.** `bootstrap_status` accepts an optional `limit: number` (default unlimited) and an optional `channel_type_filter: string`. When `limit` is provided, `recent[]` is capped to the `limit` most-recent entries sorted by `completed_at` descending; the cap does not affect `active[]`. When `channel_type_filter` is provided, both `active[]` and `recent[]` are filtered to entries whose `channelType` exactly matches the filter string. Both parameters compose: `bootstrap_status({ limit: 5, channel_type_filter: "telegram" })` returns at most 5 recent telegram entries and all active telegram entries. Parameter validation rejects a non-positive `limit` with a structured error `{ code: "INVALID_PARAM", message: "limit must be a positive integer" }`. Unit tests for `src/k8s/bootstrap-runner.test.ts` cover: `limit` applied to a result set larger than the cap, `channel_type_filter` with mixed channel types in both maps, and the composed case.

4. **`report_step(label)` is a callable IPC tool available inside the bootstrap skill.** The bootstrap pod may call `report_step(label: string)` at any point during execution — between questions, after `npm ci` completes, during credential validation — to publish a human-readable step label to the orchestrator via the `kubeclaw:bootstrap:<bootstrapJobId>` Redis topic with payload `{ type: "step", label: string, ts: ISO8601 }`. The orchestrator's Redis subscriber (in `src/k8s/ipc-redis.ts`) records the most-recent `step` payload per `bootstrapJobId` in a in-memory map so `bootstrap_status` can return it as `currentStep` without a second Redis round-trip. The tool is registered in `src/admin-shell.ts` (exposed to the bootstrap pod's superuser agent loop alongside other IPC tools) and has a maximum label length of 200 characters enforced both client-side (truncated before publish) and server-side (truncated before storage). Unit tests confirm: (a) `report_step` publishes with the correct topic and payload shape; (b) a subsequent `bootstrap_status` call reflects the label in `currentStep`; (c) a label exceeding 200 characters is truncated to exactly 200 on both sides.

5. **Retention enforced by a background GC loop that respects `BOOTSTRAP_HISTORY_RETENTION_HOURS`.** A periodic background coroutine in the orchestrator process (interval ≈ 60 s, implemented alongside the existing GC patterns in the orchestrator startup sequence) runs `DELETE FROM bootstrap_history WHERE completed_at < datetime('now', '-N hours')` where `N = parseInt(process.env.BOOTSTRAP_HISTORY_RETENTION_HOURS ?? '24')`. Active entries (those still present in `activeBootstraps`) are never touched by the GC loop regardless of `started_at` age. The retention behaviour is validated e2e: the test overrides `BOOTSTRAP_HISTORY_RETENTION_HOURS=1` via a Helm values override on a dedicated release (e.g. `kubeclaw-bstatus`), inserts a `bootstrap_history` row with `completed_at` set to two hours ago directly into the orchestrator's SQLite file via `kubectl exec`, waits up to 70 s for the next GC cycle to fire, then calls `bootstrap_status` and asserts the row has disappeared from `recent[]`. A row with `completed_at` in the past-30-minutes must still appear, confirming the GC does not over-delete.

## Story 181: `upgrade_channel` performs a blue-green runtime PVC swap with automatic rollback on failure

**As a** KubeClaw operator who needs to apply a security fix to a running channel without waiting for a full Helm release cycle,
**I want** a single admin-shell IPC tool `upgrade_channel(instance_name, target_manifest_hash)` that provisions a new versioned runtime PVC, replays bootstrap against the target manifest, then atomically swaps the steady-state Deployment to the new PVC while preserving the old one as a fallback,
**So that** a failed upgrade — whether due to MANIFEST_DIVERGENCE, a credential gap the admin declines to fill, or an LLM skill error — leaves the running channel completely undisturbed on its previous version with zero downtime, and a successful upgrade self-cleans the old PVC after a configurable grace period.

### Background — why blue-green and not remove + bootstrap

`remove_channel` followed by `bootstrap_channel_from_skill` would achieve a similar install result, but it imposes guaranteed downtime: the Deployment is deleted before the new runtime PVC is ready. If the new bootstrap fails, the operator is left with no running channel at all and must re-bootstrap from scratch, re-entering credentials and waiting for the full `npm ci` cycle.

The blue-green model here avoids that by treating the old runtime PVC as a live fallback until the new one is proven. The channel's Secret (credentials) and any per-group data PVCs are wholly separate from the runtime PVC and belong to the channel instance, not to any particular runtime version; they are never touched by the upgrade path. Only the runtime PVC — containing `node_modules/`, `channel-entry.js`, and `package-lock.json` — is versioned and swapped.

The version suffix scheme (`-runtime-v1`, `-runtime-v2`, …) is parsed from the existing PVC name at upgrade time; a PVC without a version suffix is treated as `-v1` and the next PVC is created as `-v2`. At no point are two versions of the runtime PVC mounted simultaneously on the same pod. The old PVC remains read-only-mounted on the existing Deployment pods until the rolling update to the new PVC version is fully confirmed, at which point it is deleted after a configurable grace period (default 5 minutes). On any failure, the new PVC is deleted immediately and the Deployment is unchanged.

This model reuses the Story 174 bootstrap state machine, the Story 176 hash recomputation gate, and the Story 178 manifest registry — `upgrade_channel` is bootstrap-runner.ts with a different PVC name and a Deployment-patch commit path rather than a Deployment-create path.

### Acceptance criteria

1. **Happy path: new versioned PVC created, packages installed, Deployment patched, old PVC deleted after grace period.** Call `upgrade_channel("<instance>", "<v2-hash>")` against a running Telegram channel whose steady-state Deployment mounts `kubeclaw-channel-<instance>-runtime-v1`. Within the bootstrap deadline: PVC `kubeclaw-channel-<instance>-runtime-v2` is created and the bootstrap Job runs `npm ci --prefix /runtime` against the v2 manifest from the `kubeclaw-channel-manifests` ConfigMap. The orchestrator independently recomputes the runtime hash (Story 176 gate) and on match calls the upgrade-path branch of `commit_channel_config`. The Deployment's volume spec is patched to reference `-runtime-v2`; `kubectl rollout status` semantics confirm all pods are running the new version before the orchestrator returns success to the admin. After the grace period (default 5 min, overridable via `UPGRADE_OLD_PVC_GRACE_SECONDS`), `kubeclaw-channel-<instance>-runtime-v1` is deleted. The channel's Secret and all PVCs with labels other than `kubeclaw.io/runtime=true` are byte-identical to their pre-upgrade state. Verified end-to-end: send a test message to the upgraded channel and observe a reply in the steady-state pod's logs, confirming the dynamically-loaded channel entry from the new PVC is serving traffic.

2. **Failure path: old PVC and Deployment untouched; channel continues serving.** Register a v2 manifest that the upgrade skill cannot satisfy — either a credential the admin declines to supply (interactive failure), a deliberate package-lock deviation that triggers MANIFEST_DIVERGENCE (Story 176), or an intentional skill error returning a non-zero exit from `local_bash`. In each case `upgrade_channel` returns a structured error `{ code: "<UPGRADE_FAILED|MANIFEST_DIVERGENCE|CREDENTIAL_REFUSED>", reason: string }`. Cluster state assertions: `kubeclaw-channel-<instance>-runtime-v2` does not exist; `kubeclaw-channel-<instance>-runtime-v1` exists and is unchanged; the Deployment's volume spec still references `-runtime-v1`; sending a test message to the channel produces a normal reply captured in the v1 pod's logs — the channel never stopped serving.

3. **Progress surfaced via SSE; `upgrade_channel` is visible in `activeBootstraps` as `state: "upgrading"`.** The upgrade operation publishes stage messages to Redis topic `kubeclaw:bootstrap:<upgradeJobId>` (same bridge as Story 174 AC4) in the following sequence: `"Creating runtime-v<N+1> PVC"`, `"Installing v<N+1> packages"`, `"Validating credentials"`, `"Patching Deployment"`, `"Rolling out v<N+1>"`, `"Deleting v<N> PVC"` on the success path; or `"Reverting; v<N> still active"` followed by the structured error on the failure path. The admin shell SSE stream receives these as ordered events. If the Story 180 `bootstrap_status` tool is implemented, the upgrade appears in its output with `channelType: "<type>"`, `instanceName: "<instance>"`, and `state: "upgrading"` while in progress; on completion the entry is removed from `activeBootstraps` exactly as an initial bootstrap completion removes its entry.

4. **Credentials reuse: skill detects existing valid credentials and skips the admin dialogue.** If the v2 skill's frontmatter declares the same credential field names as v1, the orchestrator passes the current Secret's data into the bootstrap Job pod — either as environment variables sourced from the existing Secret reference or as a mounted volume — before the skill runs. The skill validates the credentials with `local_bash` (e.g. `curl https://api.telegram.org/bot${TOKEN}/getMe` via the credential broker) and, if the validation call returns HTTP 200, calls `commit_channel_config` immediately without prompting the admin. If the v2 skill declares new credential fields not present in the existing Secret, the dialogue is interactive only for those new fields; existing-field values are pre-populated and the admin is not re-asked. An autonomous upgrade that requires no admin interaction must complete within the bootstrap deadline without any human input. Verified by: running `upgrade_channel` with a v2 skill whose credential fields are identical to v1; asserting no SSE prompt reaches the admin shell; asserting the Deployment is patched and traffic flows on the new PVC.

5. **Concurrent upgrade rejected; initial bootstrap and upgrade cannot race on the same instance.** Calling `upgrade_channel` on an instance that already has an in-progress upgrade returns `{ code: "ALREADY_IN_PROGRESS", reason: "upgrade already active for <instance>" }` without spawning a new Job or PVC. Calling `upgrade_channel` on an instance whose initial bootstrap (from `bootstrap_channel_from_skill`) is still in progress similarly returns `{ code: "ALREADY_IN_PROGRESS", reason: "bootstrap already active for <instance>" }`. The `activeBootstraps` map from Story 175 is the single authoritative lock; the upgrade path uses a composite key `<instance>:upgrade` when recording its entry, so `activeBootstraps.has("<instance>")` (initial bootstrap) and `activeBootstraps.has("<instance>:upgrade")` (upgrade) are checked independently before any cluster resource is created. After a successful or failed upgrade completes, the `<instance>:upgrade` entry is deleted from the map and a subsequent `upgrade_channel` call spawns cleanly.

## Story 184: Bootstrap audit trail — immutable compliance record of every channel install

**As a** KubeClaw operator subject to SOC 2 or ISO 27001 change-control requirements
**I want** every `bootstrap_channel_from_skill` invocation to produce an append-only, long-retention audit record capturing who initiated the install, which skill drove it, which manifest was requested and observed, and what the final outcome was
**So that** auditors can answer "who installed the Telegram channel, when, with which skill version, against which manifest hash, and did the runtime match the approved manifest?" without relying on ephemeral Kubernetes Events or short-lived operational logs

### Background — two-table separation: operational vs compliance

Story 180 introduces `bootstrap_history`, a short-retention table (24 h default) designed for operational observability: an operator or the `bootstrap_status` IPC tool can check what bootstraps are in flight, what just failed, and why. Rows in `bootstrap_history` may be updated as a job transitions through states and are purged aggressively once no longer operationally relevant.

This story introduces a second table, `bootstrap_audit`, that serves a completely different purpose: compliance and change-control. It is append-only — rows are never updated, only inserted — and long-retention (90 days default, configurable to zero for infinite retention). Every `bootstrap_channel_from_skill` call produces exactly two rows: a start row (written when the orchestrator accepts the job) and a terminal row (written when the job reaches a final state: `succeeded`, `timed-out`, `manifest-divergence`, `rejected`, or `error`). This pair represents the full lifecycle of a single bootstrap as an immutable timeline of facts.

Both tables are populated from the same orchestrator code paths inside `src/k8s/bootstrap-runner.ts`. They must not have separate insert paths that could drift independently: the function that transitions a bootstrap to a terminal state appends to both tables (or to neither, if the terminal write is transactional).

The clean separation: `bootstrap_history` is mutable and short-lived; `bootstrap_audit` is immutable and long-lived. Tooling (e.g. the `bootstrap_audit_log` IPC tool introduced here) queries only `bootstrap_audit`. Operational dashboards and `bootstrap_status` queries `bootstrap_history`. Implementers must not conflate or merge the two.

### Acceptance criteria

1. **`bootstrap_audit` table created on orchestrator startup via idempotent migration.** The full schema — including both `CREATE INDEX` statements — is added to the `createSchema` function in `src/db.ts` using `CREATE TABLE IF NOT EXISTS` and `CREATE INDEX IF NOT EXISTS`, following the pattern of every other table in that file. Running the orchestrator against an existing SQLite file that pre-dates this story applies the migration without error; running against a fresh file creates the table at first boot. The two indexes are: `bootstrap_audit_by_type ON bootstrap_audit (channel_type, recorded_at DESC)` and `bootstrap_audit_by_outcome ON bootstrap_audit (outcome, recorded_at DESC)`. Existing tests that exercise schema introspection — specifically `src/db.diag.test.ts` — must continue to pass after the new table and indexes are added, without manual test intervention. The `getDiagSnapshot` function need not count `bootstrap_audit` rows (that is a follow-on), but it must not error when the table exists.

2. **Every `bootstrap_channel_from_skill` call appends exactly two rows — a start row and a terminal row — and no row is ever updated.** When the orchestrator accepts a `bootstrap_channel_from_skill` call it immediately inserts a start row into `bootstrap_audit` with `outcome: 'in-progress'`, `recorded_at` set to the ISO-8601 wall-clock start time, `admin_identity` and `admin_session_id` from the authenticated session, `skill_content_hash` (sha256 of the skill markdown as loaded from the ConfigMap at job-spawn time), `manifest_hash_requested` (the pre-computed hash from the `kubeclaw-channel-manifests` ConfigMap for the requested `channel_type`), and `manifest_hash_observed` left NULL. On reaching a terminal state — success, timeout (Story 175), manifest divergence (Story 176), or error — the orchestrator inserts a second, separate row with the final `outcome` value, `recorded_at` set to the terminal-state wall-clock time, all hash fields populated (for `succeeded` and `manifest-divergence` outcomes, `manifest_hash_observed` carries the orchestrator-recomputed hash; for `timed-out` and `error` outcomes it is NULL), and `duration_seconds` set to the integer difference between the terminal `recorded_at` and the start `recorded_at`. No UPDATE statement is ever issued against `bootstrap_audit`. Verifiable by direct SQL query on the SQLite file after triggering a single bootstrap end-to-end: `SELECT * FROM bootstrap_audit WHERE bootstrap_job_id = ?` must return exactly two rows for a completed bootstrap.

3. **`bootstrap_audit_log` IPC tool returns filtered rows ordered by `recorded_at DESC`.** The tool is registered in `src/admin-shell.ts`'s `TOOLS` array (after the `bootstrap_channel_from_skill` entry) and handled in `runToolCall` / the HTTP `POST /tool` handler. Its parameters are all optional: `limit` (integer, default 50, max 500), `channel_type` (string), `outcome` (string, one of the five outcome values or `'in-progress'`), and `since` (ISO-8601 datetime string). When multiple filters are supplied they compose with AND. With no filters the tool returns the most-recent `limit` rows across all channel types and outcomes. Rows are returned as a JSON array with every column of `bootstrap_audit` present. The `limit` cap is enforced server-side in the SQL query — a caller supplying `limit: 1000` receives at most 500 rows. The `since` filter compares `recorded_at` using `datetime(recorded_at) >= datetime(?)`. The underlying query function lives in `src/skills/orchestrator/bootstrap-audit.ts` alongside the GC loop (AC5) and is exported for direct unit-test use. Behaviour verified at integration level using an in-memory SQLite instance seeded with synthetic rows.

4. **Admin identity is captured from the authenticated HTTP session.** The `checkAuth` function in `src/admin-shell.ts`'s `startHttpAdminServer` already returns the authenticated username (or the value of `ADMIN_HTTP_USERNAME` when no password is configured). Every code path that calls `bootstrap_channel_from_skill` — whether dispatched via the LLM agent loop (`runAgenticTurn`) or called directly through the `POST /tool` HTTP handler — must forward the authenticated `user` string as `admin_identity` when constructing the start-row insert. The session identifier is extracted from a request-scoped UUID generated at SSE subscription time (the `SseAdminClient` interface in `admin-shell.ts` gains a `sessionId: string` field, populated with `crypto.randomUUID()` on `GET /events` registration); this value is threaded through to `admin_session_id` in the audit row. When the admin shell is started without a password (`ADMIN_HTTP_PASSWORD` unset or empty), `checkAuth` returns `username` directly; in this case `admin_identity` is `"anonymous"` and `admin_session_id` is still the per-SSE-connection UUID. Integration tests for this AC may use the existing admin shell HTTP test harness pattern from `e2e/minikube-live-admin-shell.test.ts` (Basic Auth user `alice`, session UUID extracted from the SSE connection setup). For dev-mode (no-auth) tests, the test should carry an `xfail` annotation with a warning comment that audit logs are not compliance-grade when authentication is disabled.

5. **Background GC purges rows older than `BOOTSTRAP_AUDIT_RETENTION_DAYS`; setting to `0` disables GC.** A `startBootstrapAuditGcInterval()` function in `src/skills/orchestrator/bootstrap-audit.ts` mirrors `startToolJobPruneInterval` in `src/channel-runner.ts` exactly: it reads `BOOTSTRAP_AUDIT_RETENTION_DAYS` from `process.env` (default `"90"`, parsed as integer), schedules a `setInterval` at a configurable `BOOTSTRAP_AUDIT_GC_INTERVAL_MS` (default 3 600 000 ms, one hour), and inside each tick calls `pruneBootstrapAudit(retentionDays)` which deletes rows whose `recorded_at` is older than the retention window. When `BOOTSTRAP_AUDIT_RETENTION_DAYS=0` the function returns without scheduling anything (infinite retention). Each GC pass emits a structured log line `{ event: "bootstrap_audit_gc", deleted_rows: N }` at `info` level using the project's `logger` — even when `N` is zero. The `pruneBootstrapAudit` function is exported for direct unit-test invocation. To verify the retention boundary: insert a synthetic row via the test helper with `recorded_at` set to an ISO-8601 timestamp 25 hours in the past, then call `pruneBootstrapAudit(1)` directly and assert it returns `1` and the row is gone. Setting `BOOTSTRAP_AUDIT_RETENTION_DAYS=0` and calling `pruneBootstrapAudit(0)` must return `0` without deleting any rows, matching the behaviour of `pruneOldToolJobs(0)`.
