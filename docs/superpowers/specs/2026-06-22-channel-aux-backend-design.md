# Channel Auxiliary Backend (per-channel sidecar) — Design Spec

**Date:** 2026-06-22
**Status:** Draft — awaiting user review
**Goal (one sentence):** Generalize the channel manifest so a channel can declare an **auxiliary backend container**, rendered as a per-channel **sidecar** in the channel pod, and migrate the Signal channel from its bespoke shared `signal-cli` StatefulSet onto this abstraction.

## Why

Most KubeClaw channels (`irc`, `oauth-webchat`, `http`) are self-contained: a `channel-entry.js` adapter that talks directly to its platform. **Signal can't be self-contained** — it needs `signal-cli` (a stateful, registered Signal client) which has no viable embeddable JS library (see `docs/superpowers/` research: the official lib is native + crypto-only + AGPL; the only complete JS port is abandoned; every serious project shells to a daemon). So Signal is offloaded to a daemon.

Today that daemon is a **bespoke `kubeclaw-signal-cli` StatefulSet** + a hand-coded egress NetworkPolicy + a shared account — a special case living outside the channel install mechanism. This spec makes "a channel that needs a backend container" a **first-class, declarative manifest concept**, so:
- Signal stops being two hand-maintained Helm templates and becomes one instance of a reusable pattern (future WhatsApp `whatsmeow`, Matrix bridges, etc. fit the same field).
- The backend's create/lifecycle/removal flow through the existing one-mechanism model (bootstrap / declarative Helm / `remove_channel`).

**Hosting decision (settled with the user): per-channel sidecar.** The backend runs as a sidecar container *inside each channel pod*, with its own session PVC. Each channel instance → a distinct Signal account; the backend is created and removed *with* the channel.

## Non-goals
- Embedding a Signal client in the adapter (researched, not feasible).
- A shared/co-managed backend model (explicitly rejected in favor of per-channel).
- Domain-scoped egress (K8s NetworkPolicy can't do DNS-based egress without a CNI like Cilium; out of scope — see Risks).

## Design

### 1. Manifest schema — the `sidecar` field
Add an optional `sidecar` to the channel manifest, the registry types, and validation (`src/skills/orchestrator/channel-manifest-registry.ts` — `RegisterArgs`, `OverrideRow`, the validator; mirrored in `src/channel-manifests/reconciler.ts` manifest type and the Helm `bootstrap.channelManifests.<type>` values).

```ts
sidecar?: {
  image: string;             // e.g. "bbernhard/signal-cli-rest-api:0.93"
  port: number;              // in-pod port the adapter reaches at http://localhost:<port>
  sessionMountPath: string;  // where the session PVC mounts in the sidecar
  sessionStorageGi: number;  // session PVC size
  env?: { name: string; value: string }[];  // sidecar env (e.g. MODE=native)
  healthPath?: string;       // readiness/liveness HTTP path on <port> (optional)
  egressPorts?: number[];    // ports the sidecar needs OUTBOUND (e.g. [443] to Signal servers)
}
```
**Constraints (validated):** `sidecar` is only valid when `host_mode === 'channel-runner'`; `image`/`port`/`sessionMountPath`/`sessionStorageGi` required when `sidecar` present; `port` and `egressPorts` in 1–65535; `image` non-empty.

### 2. Steady-state Deployment builder (`src/k8s/ipc-redis-bootstrap.ts`, `processCommitChannelConfig`)
When the resolved manifest has `sidecar`, the channel Deployment additionally gets:
- **A second container** `signal-cli` (named after the type, e.g. `<type>-backend`): `image`, `containerPort: port`, `env`, and — if `healthPath` set — readiness + liveness `httpGet { path: healthPath, port }`. Low-privilege securityContext consistent with the existing channel container.
- **A session PVC** `kubeclaw-channel-<inst>-auxsession` (RW), created via the existing `createPvc` dep, mounted at `sessionMountPath` on the sidecar (added to the `extraVolumes` list alongside groups/store/sessions).
- The **channel container env** gets the adapter's API URL pointed at `http://localhost:<port>` (for Signal: `SIGNAL_API_URL`). The adapter already reads this env var.

The existing groups/store/sessions PVCs + the `/runtime` RO mount are unchanged.

### 3. NetworkPolicy
- **Remove** the bespoke "channel → `kubeclaw-signal-cli:8080`" egress rule (`networkpolicies.yaml` ~L101) — the backend is now in-pod (`localhost`), no cross-pod traffic.
- A channel pod whose manifest declares `sidecar.egressPorts` gets **egress allowed on those ports** (e.g. 443) so the sidecar can reach the external service (Signal's servers/CDN). Generated by the orchestrator when it creates the channel's NetworkPolicy (bootstrap path) and by `channel-pods.yaml`/`networkpolicies.yaml` (declarative path) — not hand-coded per channel.

### 4. PVC lifecycle
- **Create:** the bootstrap `createPvc` path creates `kubeclaw-channel-<inst>-auxsession` when the manifest has `sidecar`.
- **Remove:** `src/skills/orchestrator/channel-remove.ts` deletes `kubeclaw-channel-<inst>-auxsession` — extend the anchored PVC regex (`^kubeclaw-channel-<i>-(groups|store|sessions|runtime|auxsession)(-v\d+)?$`).

### 5. Declarative Helm path (`helm/kubeclaw/templates/channel-pods.yaml`)
When the channel type's manifest (in `bootstrap.channelManifests.<type>`) declares a `sidecar`, render the second container + the session PVC (in `storage.yaml`) + the egress netpol. The declarative path reads the manifest's `sidecar` from values.

### 6. Migrate Signal onto the abstraction
- Add `sidecar` to `bootstrap.channelManifests.signal`:
  `{ image: bbernhard/signal-cli-rest-api:<pinned>, port: 8080, sessionMountPath: /home/.local/share/signal-cli, sessionStorageGi: 5, env: [{ name: MODE, value: native }], healthPath: /v1/health, egressPorts: [443] }`.
- **Adapter** (`signal/channel-entry.js`): change the `SIGNAL_API_URL` default from `http://kubeclaw-signal-cli:8080` → `http://localhost:8080`. Otherwise unchanged. Recompute the manifest hash (the `sidecar` field is part of it).
- **Delete** `helm/kubeclaw/templates/signal-cli.yaml` (the shared StatefulSet + Service) and the `signalCli` values block and the bespoke egress netpol rule.
- **Update** `bootstrap-signal.md`: the prerequisite changes from "deploy the shared daemon + link once" to **per-instance linking** — after the channel pod is up, `kubectl port-forward pod/<channel-pod> 8080:8080`, do `/v1/qrcodelink` (or register), session persists on the per-channel `-auxsession` PVC.

### 7. Account-linking operational model
Per channel instance, post-install: port-forward into *that channel's pod* (the sidecar's `:8080`), scan the QR / register the number. The Signal session is written to the per-channel `-auxsession` PVC and survives restarts. (Still manual, still not CI-able — intrinsic to Signal.)

### 8. Docs
- New section in `docs/DEVELOPING_A_CHANNEL.md` (or a short new doc): the **"channel-with-external-backend"** category + the `sidecar` manifest field, with Signal as the worked example. Update `docs/INSTALLING_A_CHANNEL.md`'s Signal notes for per-instance linking.

## Testing (all three levels)
- **Unit:** (a) manifest validation accepts a valid `sidecar`, rejects it when `host_mode !== channel-runner` and when required subfields are missing; (b) the Deployment builder renders the 2nd container + the `-auxsession` PVC volume/mount + the `localhost` API-URL env when `sidecar` present, and does NOT when absent; (c) `remove_channel` deletes `-auxsession`.
- **Integration:** `helm template` renders the sidecar container + session PVC + egress netpol for a sidecar-bearing channel; no `signal-cli.yaml` output remains.
- **E2e:** extend `e2e/minikube-live-channel-declarative-install-remove.test.ts` (or a sibling) to declaratively install a sidecar-bearing channel and assert: the pod has 2 containers, the `-auxsession` PVC exists, and `remove_channel` cleans everything including `-auxsession`. Use a lightweight stand-in sidecar image (e.g. a tiny HTTP echo) so the test validates the *rendering + lifecycle* without needing a real Signal account (a real Signal round-trip remains untestable in CI — call this out explicitly in the test).

## Migration / compatibility
Removing the shared `signal-cli.yaml` is a **breaking change for any existing Signal install** (each channel must now link its own account). Signal is brand-new and unproven (no live deployments), so impact is ~nil. Document in the changelog + `bootstrap-signal.md`.

## Risks / open points
- **Egress breadth:** `egressPorts: [443]` lets the sidecar reach *any* host on 443, not just Signal's. K8s NetworkPolicy can't scope egress by domain without a CNI like Cilium. Accept for now; note in docs. (Cilium FQDN policy is a possible future tightening.)
- **Stateful channel pod:** the `-auxsession` PVC makes a sidecar-backed channel pod stateful (unlike the other, replaceable channel pods). Acceptable and inherent for backend-bearing channels; the channel's own `/runtime` stays RO.
- **Declarative-path complexity:** rendering the sidecar from `bootstrap.channelManifests.<type>.sidecar` in `channel-pods.yaml` is the fiddliest part; the bootstrap path (TS builder) is the primary, better-tested route.
