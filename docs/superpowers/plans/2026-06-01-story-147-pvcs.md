# Story 147: Helm chart PVCs — persistent volume claims for sessions + groups + Redis

## Goal

Verify that the helm chart renders and binds `PersistentVolumeClaim` objects for orchestrator session data (`kubeclaw-sessions`), per-group volumes (`kubeclaw-groups`), project directory (`kubeclaw-project`), and SQLite/orchestrator state (`kubeclaw-store`), each with the correct size and a `Bound` phase after helm install.

## Architecture

PVC resources are defined in two helm templates:

- `helm/kubeclaw/templates/storage.yaml` — four top-level PVCs (`kubeclaw-groups`, `kubeclaw-sessions`, `kubeclaw-project`, `kubeclaw-store`) plus per-channel PVCs (generated from `.Values.channels`). The `kubeclaw-store` PVC is always `ReadWriteOnce`; the others honour `.Values.storage.accessMode`. All use the `kubeclaw.storageClassName` helper.
- `helm/kubeclaw/templates/redis.yaml` — a `StatefulSet` with a `volumeClaimTemplates` entry (`data`, `ReadWriteOnce`) sized from `.Values.redis.storage`. Redis storage is managed by Kubernetes via the StatefulSet controller rather than a standalone PVC.

Per-channel PVCs (`kubeclaw-channel-<name>-groups`, `-store`, `-sessions`) carry `helm.sh/resource-policy: keep` on the groups and store PVCs so that `helm upgrade` and `helm uninstall` do not destroy conversation history or the SQLite database (Story 35).

## Tech Stack

- **Test runner:** vitest e2e (`npm run test:e2e`)
- **Cluster:** real minikube/kind cluster with `requireKubernetes()` guard
- **Helm:** pre-installed release via global-setup; tests use `kcSafe` / `getJson` helpers
- **Storage:** default minikube storage class (standard / hostpath provisioner)
- **LLM dependence:** none

## Tasks (retrospective)

### AC 1 — `kubeclaw-groups` PVC is Bound with size 50Gi

`storage.yaml` renders a `PersistentVolumeClaim` named `kubeclaw-groups` with `accessModes: [{{ .Values.storage.accessMode }}]` and `storage: {{ .Values.storage.sizes.groups }}`. The e2e test polls `kubectl get pvc kubeclaw-groups -o jsonpath={.status.phase}` until `Bound`, then asserts both `phase == Bound` and `spec.resources.requests.storage == 50Gi`.

### AC 2 — `kubeclaw-sessions` PVC is Bound with size 20Gi

`storage.yaml` renders `kubeclaw-sessions` identically to groups. The e2e test asserts `Bound` and `20Gi`.

### AC 3 — `kubeclaw-project` PVC is Bound with size 10Gi

`storage.yaml` renders `kubeclaw-project` for the orchestrator project directory mount. The e2e test asserts `Bound` and `10Gi`.

### AC 4 — `kubeclaw-store` PVC is Bound with size 1Gi

`storage.yaml` renders `kubeclaw-store` with a hardcoded `ReadWriteOnce` access mode (SQLite requires exclusive write access). The e2e test asserts `Bound` and `1Gi`.

### Redis PVC

The Redis data volume is managed as a `volumeClaimTemplates` entry inside the `StatefulSet` in `redis.yaml`. It uses `ReadWriteOnce` and is sized from `.Values.redis.storage`. No standalone Redis PVC test is included in this story; the StatefulSet binding is covered by the Redis liveness checks in other describe blocks.

### Verification

Run: `npm run test:e2e -- helm-chart -t "persistent volume claims"`

Expected: **4 / 4 tests pass** (all four top-level PVCs Bound at correct sizes).

Runtime: ~25–30 seconds (PVCs bind quickly on minikube hostpath provisioner; `waitUntil` timeout is configured per `PVC_BIND_TIMEOUT`).
