# Story 148 Retrospective: Sidecar ACL Key Isolation

**Date:** 2026-06-01
**Story:** 148 — Sidecar ACL Key Isolation — sidecar can't write to other jobs' streams
**Status:** passing 1/1

## Summary

Story 148 verifies that Redis ACL key patterns isolate sidecar credentials by job-id, so
a misbehaving sidecar cannot read or write keys belonging to a different job.

## What was implemented

The key-pattern ACL enforcement lives entirely in `src/k8s/acl-manager.ts` inside
`RedisACLManager.createJobACL()`. When provisioning a sidecar user the manager passes
`~kubeclaw:*:<jobId>` as the key-pattern rule (in the production path) or an equivalent
`~kubeclaw:*:<jobId>` glob to `ACL SETUSER`. The e2e test constructs the ACL users
directly with the same glob pattern and verifies:

1. Each sidecar user can SET/GET its own `kubeclaw:data:<jobId>` key.
2. Each sidecar user receives NOPERM when attempting to access the other job's key.

## ACL pattern design in acl-manager.ts

`createJobACL` builds the ACL rules array:

```
%R~kubeclaw:input:<jobId>     // read-only on own input stream
resetchannels
&kubeclaw:messages:<groupFolder>  // publish to own group channel
+xread +xrange +publish +ping +reset +quit
```

The production ACL is intentionally narrow (read-only input stream + publish channel).
The e2e Key Isolation test uses a simpler `~kubeclaw:*:<jobId>` glob with `+@read
+@write` to validate the isolation property independently of the full production ruleset.
