# Story 112: In-cluster Redis enforces authentication (NOAUTH / WRONGPASS / accept correct)

## Goal

Verify that the in-cluster Redis StatefulSet rejects unauthenticated connections with NOAUTH, rejects wrong-password connections, and accepts connections with the correct admin credentials for normal operations. All tests run against the real minikube Redis via the global-setup port-forward on `localhost:16379`.

## Architecture

Redis authentication is enforced via an ACL file generated by an `init-acl` initContainer in `helm/kubeclaw/templates/redis.yaml`. The initContainer disables the `default` user (`user default off nopass`) and creates named ACL users (`orchestrator`, `channel`, `agent`, `tool-server`, `adapter`) with scoped passwords drawn from the `kubeclaw-redis` Kubernetes Secret. Redis is started with `--aclfile /data/redis-acl.conf`, so any client connecting without credentials — or with a wrong password — is rejected at the protocol level before any command is processed. The e2e test suite creates raw ioredis clients without credentials (or with a bogus password) and asserts the expected error codes, then verifies normal read/write operations with the orchestrator user credentials supplied by the global-setup.

## Tech Stack

- **Test runner:** vitest e2e (`npm run test:e2e`)
- **Cluster:** real minikube with live Redis (port-forwarded to `localhost:16379` by `e2e/global-setup.ts`)
- **Redis client:** ioredis — shared orchestrator client from `e2e/setup.ts` for happy-path tests; raw `lazyConnect` clients for rejection tests
- **Auth mechanism:** Redis ACL file (`--aclfile`) — no `requirepass`, ACL-based per-user passwords
- **LLM dependence:** none

## File Structure

| Path | Role |
|------|------|
| `e2e/redis-auth.test.ts` | e2e suite — 4 `it()` tests covering NOAUTH, WRONGPASS, and two correct-credential flows |
| `e2e/setup.ts` | `getSharedRedis()` — returns the orchestrator-authed ioredis client established in `beforeAll` |
| `e2e/global-setup.ts` | Starts port-forward, verifies ACL connectivity, exposes `localhost:16379` |

| `helm/kubeclaw/templates/secrets.yaml` | Generates and persists per-user Redis passwords in the `kubeclaw-redis` Secret |

## Tasks (retrospective)

### AC 1 — No-password connection rejected with NOAUTH

`it('rejects connection with no password')` instantiates a bare ioredis client (no `password` field, `lazyConnect: true`, `maxRetriesPerRequest: 1`) pointing at the port-forwarded host/port extracted from the shared orchestrator client. Calling `ping()` throws; the test asserts `err.message` matches `/NOAUTH|WRONGPASS|Authentication required/i`. The ACL `default off nopass` entry ensures no client can connect anonymously.

### AC 2 — Wrong-password connection rejected with WRONGPASS

`it('rejects connection with wrong password')` uses the same pattern with `password: 'definitely-wrong-password-xyzzy'`. Redis rejects the AUTH command and ioredis surfaces the error; the test asserts the message matches `/WRONGPASS|NOAUTH|invalid|password/i`. In practice the cluster returns `NOAUTH` because the default user is disabled — this satisfies the intent of the AC.

### AC 3 — Correct credentials succeed for normal ops

Two tests cover this: `it('correct credentials allow ping')` calls `redis.ping()` on the shared orchestrator client and asserts `'PONG'`. `it('correct credentials allow read and write')` sets a TTL'd key, reads it back, and asserts the value matches, confirming full read/write access.

### AC 4 — Tests run against in-cluster Redis via global-setup port-forward

`e2e/global-setup.ts` establishes the port-forward before any test file loads. `getSharedRedis()` in `e2e/setup.ts` returns the ioredis client connected to `localhost:16379`; rejection tests extract `host`/`port` from that client's options to target the same endpoint. No test hard-codes an address.

### AC 5 — Deterministic auth enforcement

Auth enforcement is handled at the Redis server level (ACL file loaded at startup) rather than in application code. The `init-acl` initContainer writes the file once; Redis reads it on start. This is deterministic — no runtime toggle, no race, no eventual-consistency window.

## Verification

Run: `npm run test:e2e -- redis-auth`

Expected: **4 / 4 tests pass** (correct credentials ping, NOAUTH rejection, WRONGPASS rejection, correct credentials read/write).

Runtime: < 5 seconds (no helm install, no rollout wait; Redis already running from global-setup).
