# Story 136: Message Accumulation — Burst-in Messages Coalesce into One LLM Turn

> **Retrospective plan** — implementation already exists; all tests pass. Tasks below describe what was built and how it was verified.

**Goal:** Verify that consecutive inbound messages within a group are accumulated into a single LLM prompt rather than triggering one agent call per message. Per-group debounce is independent, chunk ordering is preserved, and the configured debounce period is honored.

**Architecture:** The accumulation logic lives entirely in `src/channel-runner.ts` inside `processGroupMessages()`. The key mechanism:

1. `getMessagesSince(chatJid, lastAgentTimestamp[chatJid], ASSISTANT_NAME)` fetches all messages received since the last agent run cursor — returning a slice of the DB ordered by timestamp, not just the most-recent one.
2. The caller (the `GroupQueue` debounce loop) gates when `processGroupMessages` fires, so the window for accumulation is the debounce period configured per group.
3. All collected messages pass through a slash-command filter loop; non-command messages accumulate in `normalMessages`.
4. `formatMessages(normalMessages, TIMEZONE)` serialises the entire batch as a single XML prompt sent to the LLM in one call.

The per-group isolation falls out naturally: `lastAgentTimestamp` is keyed by `chatJid`, and the `GroupQueue` maintains a separate debounce timer per JID.

**Tech Stack:** vitest (e2e runner with `--reporter=verbose`), SQLite in-memory DB (`_initTestDatabase`), mock channel (`./lib/mock-channel.ts`), mock LLM runner (`vi.mock('../src/runtime/index.js')`). No Kubernetes, no Redis cluster required.
