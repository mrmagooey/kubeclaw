# Story 133: Atomic State Updates — Concurrent Updates to the Same Key Linearize

> **Retrospective plan** — implementation already exists; all tests pass. Tasks below describe what was built and how it was verified.

**Goal:** Verify that concurrent updates to the same Redis key are linearized with no lost updates, using MULTI/EXEC pipelines, WATCH/optimistic-locking, HSCAN, and Lua scripts against in-cluster Redis.

**Architecture:** All atomic primitives are exercised directly against the shared Redis instance obtained via `getSharedRedis()` in the test harness. The implementation primitives live in `src/k8s/ipc-redis.ts` (ioredis client). The four strategies tested are:
- **MULTI/EXEC pipeline** — pipeline queues SET + INCR + INCR + GET in a single batch; Redis executes the batch atomically, guaranteeing no interleaving.
- **WATCH / optimistic locking** — `WATCH key` marks a key for observation; if it changes before `MULTI/EXEC`, `exec()` returns `null` (abort); the caller retries up to 3 times.
- **HSCAN** — iterates all hash fields with a cursor; does not lock the hash but is safe for read-only scans of hash state without snapshot inconsistency.
- **Lua `eval`** — a server-side script runs GET + arithmetic + SET atomically; Redis guarantees no other command runs between the GET and SET.

**Tech Stack:** vitest (e2e runner), ioredis, in-cluster Redis (`redis://orchestrator:<pass>@localhost:16379` via port-forward), no Helm install required.
