# Story 127: State TTL — expired session keys are reclaimed

## Goal

Verify that Redis-backed session keys respect TTL/expiration semantics: keys written with a TTL are reclaimed after the window elapses, refreshing a key's TTL works atomically, and sorted-set timestamps can stand in for per-field TTL on hashes.

## Architecture

TTL handling is a property of Redis itself — the orchestrator uses ioredis commands (`SET … EX`, `KEEPTTL`, `TTL`, `ZADD`, `ZREMRANGEBYSCORE`) directly from `src/k8s/ipc-redis.ts`. No custom expiry logic lives in application code; the tests exercise ioredis's wire behaviour against a live Redis instance reachable via `getSharedRedis()`. The describe block at line 288 of `e2e/state-persistence.test.ts` covers five acceptance criteria:

1. Key written with `EX 2` has positive TTL and becomes `null` after 2 s.
2. Key written with `EX 5` reports TTL ≤ 5 immediately after write.
3. Re-writing a key with `KEEPTTL` preserves its remaining TTL (stays > 5 s on a key originally set to 10 s).
4. Sorted-set scores act as per-field expiry metadata; earlier score < later score assertion confirms ordering.
5. `ZREMRANGEBYSCORE` prunes stale activity members while retaining current ones.

All five tests skip gracefully (`console.warn`) when Redis is unavailable, so the suite is safe to run in environments without a cluster.

## Tech Stack

- **Test runner:** vitest e2e (`npm run test:e2e -- state-persistence -t "TTL/Expiration"`)
- **Redis client:** ioredis (shared instance from `e2e/lib/` via `getSharedRedis()`)
- **LLM dependence:** none
- **Cluster dependence:** live Redis required; tests self-skip otherwise

## Tasks (retrospective)

### AC 1 — Write with TTL N + read within N → value; read after N → null

`redis.set(key, value, 'EX', 2)` followed by `redis.ttl(key)` asserts TTL ∈ (0, 2]. A polling loop (100 ms intervals, 5 s deadline) waits for `redis.get(key)` to return `null`, confirming key reclamation after expiry.

### AC 2 — TTL on session state is bounded immediately after write

`redis.set(sessionKey, value, 'EX', 5)` and `redis.ttl(sessionKey)` asserts TTL ∈ (0, 5].

### AC 3 — Re-write with KEEPTTL preserves remaining TTL

`redis.set(key, value, 'EX', 10)` sets the window; a subsequent `redis.set(key, updatedValue, 'KEEPTTL')` leaves the TTL intact; `redis.ttl(key)` asserts TTL > 5 (still more than half the window remaining).

### AC 4 — EXPIRE refresh via sorted-set scores updates atomically

`redis.zadd(metaKey, timestamp + 5000, 'field1')` and `redis.zadd(metaKey, timestamp + 10000, 'field2')` record expiry timestamps; `redis.zscore` retrieves them and asserts `score(field1) < score(field2)`.

### AC 5 — `ZREMRANGEBYSCORE` prunes stale activity

One member is added with score `Date.now() - 3600000` (one hour ago) and another with `Date.now()`. `redis.zremrangebyscore(key, 0, oneHourAgo)` removes the stale entry; `redis.zrange` confirms exactly one member remains.
